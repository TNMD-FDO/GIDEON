# The frontend's built-in tools for end users

The pinned frontend's built-in tools — `time`, `user_input` (`ask_user`), `subagents`, `notifications`, `chats`, `files`, `knowledge`, `memory`, `web_search`, `image_generation`, `code_interpreter`, `notes`, `channels`, `tasks`, `automations`, `calendar`, and the `terminal` capability's tools beside them — stay off on every GIDEON model record through `v1.0.0`. No category reaches an end user, and the engine's shipped flag set (spec §5.3) carries no tool-call parser. Enabling any category, and the engine flags that would make one work (`--enable-auto-tool-choice --tool-call-parser`), are out of scope.

## Why this is out of scope

**Both branches are designed around the frontend's native tool loop, so a built-in tool costs a design, not a toggle.** General's search (spec §15) runs only under `params.function_calling: legacy` on its record, and `legacy` is the same switch that stops the frontend attaching any built-in tool at all (`docs/research/owui-model-record.md` §3.2; `docs/research/owui-preset-system-prompt.md` §4.1): under the default `native` mode the composer's search toggle expects the `search_web` and `fetch_url` tools and the non-tool path — queries from the task model, pages whole into context, three results a query, the page bound — never runs. So the smallest built-in tool on General, a clarifying question back to the user, means `native` mode and with it a redesign of General's search as a model-called tool, with its own eval under ADR-0017. Research never enters the loop: the query plan is one structured-output call (§11.1), its named tools are structured queries the plan selects and the model never writes (§11.6, §14.4), and the Research service owns the turn (§13.1; ADR-0022). The engine's tool-call parser — a §5.3 supersession — would exist for the built-in tools alone.

**The `time` category is ruled out on its own.** `calculate_timestamp` is date arithmetic by a model-called tool: ADR-0006's tier 3, "none in v1", and the deadline family's reason. Whatever later ruling reopens the rest, `time` stays off.

**The deadline guardrail's guarantee is proven over a stream with no tools.** `docs/research/owui-stream-hook.md` §8 catalogues the chunk shapes for a stack with no Pipes and no Tools, and that is the stream slice-1 tickets 09 and 10 proved the lag window on. A native tool turn is several engine calls with tool messages between them; the Filter's stream hook reads text keys only and passes a `tool_calls` delta untouched; a date the user supplies through `ask_user` arrives as a tool message, outside the user message the restatement rule's exemptions read. Any category needs ticket 10's guarantee — a matched span never reaches the screen — re-proved over the tool-call shapes with the turn harness: a proof, not a setting.

**The tools are hidden, and nobody asked for them.** They are tools the frontend injects into a browser turn without the user or the model's operator naming them — the pinned middleware's own comment says API callers "don't expect hidden tools" — a surface outside the spec's model of the frontend as transport and bookkeeping (ADR-0022). No demand is on record: the harvest's 40 questions went to search and doctrine (greenfield [06]'s framing fact), and the three candidates slice-1 ticket 26's discovery named (`ask_user`, `notifications`, `subagents`) were a session's guess. ADR-0017 asks for a measure before a mechanism.

Ruled by the CSA on slice-1 ticket 27, 2026-09-08.

## When to reconsider

A user's ask, after go-live (spec §22.3's Phase C), for something a named category does — a clarifying question before an answer (`user_input`), a notification when a long answer finishes (`notifications`), a delegated sub-task (`subagents`) — recorded on a ticket as the ask, never the chat's text (spec §19.4); or a pinned frontend whose non-tool search path no longer rides `legacy`, so a built-in tool no longer costs §15's design. The reopening ticket carries the whole cost, in order: (1) the lock's `enable-auto-tool-choice` and `tool-call-parser` flags, the parser name verified against the pinned engine and model (ticket 26 read `hermes` for Qwen3; a later tag's may differ), a §5.3 supersession by a spec-bug comment or an ADR, never a flag added on the side; (2) `native` mode on the record and the §15 search redesign it forces, with an E-register entry whose `off` baseline is the non-tool path as it ships; (3) a category-by-category ruling through `meta.builtinTools` — `time` off under ADR-0006 whatever else; `files`, `knowledge`, `memory`, `code_interpreter`, and `image_generation` closed already by the capabilities §15 turns off; `notifications` behind the frontend's user-webhooks flag and the `webhooks` permission; `subagents` behind its own config flag; `chats` a read of the user's other chats — each read against §15's list and §4.2's permission set; (4) the deadline guardrail re-proved over the tool-call stream shapes — the hooks' cadence across the loop, the lag window's hold at a tool call, the supplied-date exemptions over a tool message; (5) the E-register entry per ADR-0017. More than one cycle by CLAUDE.md's sizing rule: the engine flags and the search redesign first, the categories and the guardrail after.
