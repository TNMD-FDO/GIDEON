# Changelog - Week 1, 03-09-2026, V. 0.0.25

**Release Date**: Week 1, 03-09-2026 at 14:14
**Version**: 0.0.25 (previously 0.0.24)
**Object**: install, upgrade, and rollback: gideon install runs the receiving-office sequence (preflight → apply → users reconcile → an inert engine-verify → backup run → backup drill → an install row → the URL) as one ordered command over the day-two commands; gideon upgrade <tag> takes the pre-upgrade set (its manifest the rollback's record, reused on a re-run), moves the checkout as its owner, and hands over to the new tree's own provision, preflight, and apply as streamed children, refusing a major cross without --acknowledge-breaking after printing the release note's Breaking section; gideon upgrade --rollback restores that set through restore --from staging --set <label> and re-applies the previous release, a whole stack first getting a safety set, resumable from a small in-progress record; the wait-online provision step (slice-0 ticket 08, first of two releases)
**Code review**: `docs/3-code-review/CR_w1_v0.0.25.md` (Codex loop, 4 rounds -> APPROVED)

## Changes

- **`gideon install`** (`gideon/host/install.py`; spec §3.6 step 5): the receiving-office sequence as one ordered command over commands that already exist, run in-process from a data table of phases — `preflight` → `apply` → `reconcile` (`users reconcile --now`) → `engine-verify` (an inert row until slice 1, §6.7) → `backup` (`backup run`) → `drill` (`backup drill`) → `audit` → `url`. Every nested command prints its own rows, install one phase row after each; a failed phase stops the run with a fix naming the nested command to run by hand. An `install` row with phase `intent` is written once apply has converged the stores (a failure in preflight or apply leaves no row — the writer does not exist yet), then `applied` or `failed` with the phase durations and the set label; `https://<hostname>/` is the last line. Re-running on a live box is a no-op apply, an incremental set, a drill, and the URL. Install opens with preflight (a strengthening of §3.6 step 5, recorded on the ticket).
- **`gideon upgrade <tag> [--acknowledge-breaking]`** (`gideon/host/upgrade.py`; §3.6 step 7, §2.1): runs from the *current* tree and, after the checkout, hands over to the new tree's own CLI — `host provision`, `preflight`, `apply` as children whose rows stream to the operator through the seam's new passthrough run (`Host.run(passthrough=True)`, the parent's streams flushed first). The module carries no function-level import, and a test holds it to that, so nothing of the new tree is ever loaded into the old process. Every git call runs as the checkout's owner (resolved from the directory's uid, through `sudo -u` when not root), so the owner's GitHub credentials fetch and no root-owned file lands in the tree; a dirty tree refuses first. The tag's tree must declare the tag's version; versions compare by SemVer 2.0 precedence (`Version`, pre-release identifiers included); a lower tag refuses naming `upgrade --rollback` and `restore`, an equal one is a re-run, a different major prints the `## Breaking` section of the tag's release note (`docs/2-changelog/*_v<version>.md` in the tag's tree, the one changelog surface — §2.2's root file is a recorded spec gap) and refuses without the flag. **The pre-upgrade set is the upgrade's record**: `pre-<tag>`, a full set whose manifest must record the commit the checkout is leaving (backup's root git probe now grants `safe.directory` so it never records `unknown`); `pre-<tag>-<ts>` when the plain label exists from an attempt that never crossed the checkout; reused, never re-taken, when the checkout already stands at the tag. Verify reads the new tree's `--version`, the applied record, and every service `compose config --services` declares — not only the containers `ps` lists. A failed row's fix is the standing next step by position: re-run before the checkout; reboot or correct and re-run at the new tree's provision or preflight (the checkout made, the set reused — a `reboot-required` step stops here, before anything of the product changed); `upgrade --rollback` at or after its apply.
- **`gideon upgrade --rollback [<tag>]`** (ADR-0005): the newest complete `pre-<tag>[-<ts>]` set (or the tag's) — an operator's other `pre-*` labels and the `pre-rollback-*` safety sets are never candidates — its commit in the checkout, its manifest the release and the archive boundary. Whether a restore is needed is judged from `rendered/manifest.yaml`, apply's first write: a manifest still naming the set's release means the new release never rendered and the rollback only moves the checkout back and re-applies. The verdict is written to `/data/backup-staging/rollback.json` (beside `push.json`, outside every restore root and backup root) and a re-run resumes from it — the one deviation from the plan, found in review: a restore that fails past its files stage leaves both rendered files naming the set's release, so no file-derived judgement could tell a finished rollback from a half-done one or know Postgres still needed the restore. A whole declared stack first gets a `pre-rollback-<ts>` safety set from the *current* tree (so its files, checkout, and database describe one release); a partial or stopped one gets none, said so; then `compose down`, the checkout to the release tag pointing at the manifest's commit (else the commit), the previous tree's `restore --from staging --set <label>` and `apply` as children, verify, and the `rollback` rows (the intent row deferred when Postgres is down, carried as `intent_recorded`). Host state converged for the newer release stays. The record's fields are validated, never coerced, and it goes only once the applied row is written.
- **`restore --from staging --set <label>`** (`gideon/host/restore.py`, `backupset.select_set_by_label`): the one §20.2 surface addition — the named complete set restored to its own archive boundary (no `--at` can address the newest set: selection is by finish time, the bound by archive boundary), refused with `--at` (at parse time too) or `--from target`; the pgBackRest target keeps the boundary's microseconds (pgBackRest's time format takes up to six fractional digits), which a whole-second target would have stopped short of.
- **The `wait-online` provision step** (`gideon/host/steps/network.py`, after `platform`): a drop-in makes `systemd-networkd-wait-online` accept any one link online, so the box's unplugged second port no longer fails the unit at every boot (ticket 07's hand-over); `daemon-reload` and `reset-failed` on apply; the unit's own state is never a check criterion.
- **Records**: the TRIP-3 `breaking-section` block (a major release's note carries `## Breaking`; `docs/agents/tooling.md` §4 row); `CONTEXT.md` gains *Pre-upgrade set* and *Rollback*; ticket 08 carries the rulings, five spec gaps (where the new tree's provision runs, the changelog surface, `--set`, `wait-online`, install opening with preflight), the review's four corrections and the marker deviation, and the on-box lesson; the install/upgrade runbook (`08-install-upgrade-runbook.md`) and the backup runbook's §6.
