## Changes

- **`gideon render` is real** (spec §3.5; slice-0 ticket 04): a pure function of (site file, `host.lock`, the new `images.lock`, host facts, the release checkout's templates) → `/etc/gideon/rendered/`. The render core (`gideon/host/render/`) is an ordered registry of *artifacts* — this release ships `compose.yaml` (the Compose project with the `caddy` service) and `caddy/Caddyfile` — each naming the services that mount it (its *owners*). Text configs come from readable templates under `compose/` filled with `string.Template`; `compose.yaml` is serialized by a small in-house deterministic YAML emitter (`yamlout.py`), so the bytes depend only on this repository. `render --diff` shows what apply would change and which services it would recreate; foreign files under `rendered/` refuse; files a previous release rendered are removed; `manifest.yaml` records every file's sha256, mode, and owners plus the inputs' digests.
- **`gideon apply` is real**: an eight-stage runner (`gideon/host/apply.py`) — preconditions → render → registry (every `images.lock` digest present, via `docker manifest inspect`) → pull by digest and verify `RepoDigests` against the lock → recreate only the owners of files whose hash differs from the last successful apply (`rendered/applied.yaml`, written only after verify; every service on the first apply; owners of files this release stopped rendering come from `applied.yaml`, intersected with the current service set) → apply-manifest (a recorded no-op until a frontend exists) → verify (`compose ps --all` must equal the rendered service set, all running/healthy, then a TLS probe) → record. A standalone `render` or a failed apply never hides a needed recreate.
- **Caddy is the single ingress** (spec §1.6): HTTPS 443 only (`0.0.0.0:443:443`, no port 80, no redirect listener), `auto_https disable_certs` + explicit `tls` from the fixed homes, HSTS in Caddy only, `request_body max_size 2GB`, JSON access logs to journald, and — because no upstream exists yet — a fixed 503 placeholder at the root. The image is `caddy:2.11` pinned by OCI index digest in `images.lock` and pulled as `<registry>/caddy@<digest>`.
- **`gideon tls reload` is real** (`gideon/host/tls.py`): validates the placed material with openssl *before* Caddy is touched (parse, key matches certificate, chain verifies against `/etc/gideon/ca.pem`, name covers `hostname`, not expired; every openssl call runs with closed stdin, a bound, and `-passin pass:` so nothing can prompt), then force-recreates the Caddy service (a Compose file secret is a bind mount, so a replaced key's new inode only reaches a new container) and re-verifies. The shared ingress probe (`openssl s_client` with SNI **and** `-verify_hostname` against the office CA, then the served leaf's SHA-256 fingerprint compared with the placed file) retries a failed handshake for a just-recreated container but never a fingerprint mismatch.
- **`gideon registry mirror [--to <registry>]` is a new §20.2 command** (`gideon/host/registry.py`; recorded on the ticket as spec bug (i)): copies each `images.lock` entry from its upstream *by digest* with `skopeo copy --all --preserve-digests` into the release registry (loopback pre-1.0), then proves the digest is servable; idempotent (`present` on a second run); an authenticated proxy needs `sudo` (secrets are root-only) and the command says so instead of proceeding unauthenticated. The self-hosted GitHub runner gets its first CI job, `mirror-images` — pushes to `main` only, after the hosted checks, never pull-request code.
- **Firewall**: Docker-published ports bypass ufw's INPUT rules, so the `firewall` provision step now owns a tagged `DOCKER-USER` block in `/etc/ufw/after.rules` — packets from Docker bridges (`docker0`, `br-+`) return first, `lan_cidrs` may reach 443, the libvirt bridge may reach the registry's 5000, everything else toward a published port is dropped by original destination port (no interface name, no source-range exemption) — and its check demands the owned rules at the exact head of the live chain. Verified live: `iptables-restore --noflush` rebuilds a declared chain from the file. `host-tools` now converges `skopeo` beside `ldap-utils`.
- **Riders from ticket 03**: `host.lock` `kernel_tested: "7.0.0-30-generic"`; `config/site.example.yaml` corrected to TNMD's live facts (`lan_cidrs`, SMTP host, backup path); `config/egress.yaml` v3 adds Docker Hub's blob CDN (`production.cloudfront.docker.com`, answers 403) that provision's own pull and the mirror both traverse.
- **Byte-stable fixtures** (spec §3.4): `config/site.example.yaml` and a synthetic second office (`tests/fixtures/site/second-office.yaml`: loopback registry, proxy set, search off, several districts, non-default ports) render to committed bytes under `tests/fixtures/render/`; `tests/regenerate_render_fixtures.py` rewrites them deliberately.
- **Spec bugs recorded on the ticket** (never improvised around): (g) the release registry stays a host service — apply pulls from it, so it must predate the Compose project (§20.1's row and ADR-0007's line superseded by ADR-0029); (h) render runs before any image pull, so it is stdlib + yaml on the bare-host path, not Jinja2 in a CLI image; (i) `registry mirror` added, skopeo for `crane copy`; (j) `tls reload` recreates rather than `caddy reload --force`; (k) ufw stays provision's, not render's; (l) no HTTP→HTTPS redirect under "443 only".
- **On-box first pass** (`.scratch/slice-0/assets/04-apply-first-pass.txt`): provision applied the two riders then converged 17/17; `registry mirror` served `caddy:2.11` under the exact upstream digest; `apply` passed all eight stages and the second apply recreated nothing; `https://<hostname>/` answers the 503 placeholder over the AD CS chain with HSTS, port 80 closed, zero ACME activity; `tls reload` recreated Caddy and re-verified. Acceptance criteria 2–4 closed; criteria 1 and 5 close on this release's green CI runs.
