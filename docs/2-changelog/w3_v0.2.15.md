## Changes

This release implements general-turn ticket 02 under the plan `docs/1-plans/pass-through-completion.plan.md`: `gideon-api` serves `POST /v1/chat/completions` by handing the caller's request to `gideon-generator` and returning what the engine answers, unjudged. It is the tracer through every layer the judged turn (ticket 06) will use — the key's refusal before any upstream call, the engine client's completion bound, the relay's flush behaviour on both sides, the content-free log, and the mechanism that closes the upstream when the caller leaves. No Filter is involved, the frontend still names the engine, and the service's only callers are this ticket's tests and its proof. A patch: no site key, no `/etc/gideon` contract change, no image change, so `images.lock` is untouched and nothing is built on the box.

- **The relay** (`gideon/api/relay.py`, new): **the engine's answer decides the shape, never the request.** The route sends the caller's body bytes and `Content-Type` to the engine unparsed — the model id and every other field pass by construction, the bearer becomes the engine's key, and none of the caller's other headers is forwarded. A 200 whose media type is `text/event-stream` is relayed one `aiter_raw()` chunk per body message, the engine's content-type header as sent and no length; anything else is read whole and returned under the engine's status, content type, and bytes. The media type is compared as the text before any `;`, trimmed and case-folded, because the pinned engine sends `text/event-stream; charset=utf-8` while the contract stub sends the bare type — an exact comparison would read every real stream whole, the buffering the ticket's discovery note warns of.

- **One cancel scope spans the upstream call, for both kinds.** The endpoint is a pure ASGI callable — Starlette calls a non-function endpoint as an ASGI application — whose work runs in an `anyio` task group beside a task blocked on `receive()`; whichever finishes first cancels the group. A caller's hang-up therefore lands in whatever the work is suspended on, and httpcore closes the unfinished connection under its own shield rather than returning it to the pool, which the engine reads as its client going away. The watch is the service's own and independent of the ASGI `spec_version` the server advertises — `StreamingResponse` would notice a hang-up only at its next send at `2.4`, which ticket 06's silent lag window never reaches. The upstream response is closed in the exit path under a shielded scope. This is the scope ticket 06's lag window and trip will sit inside.

- **Failure shapes.** A transport failure or timeout before the engine's headers, or while a whole body is read, is the service's fixed 502 (`upstream_unavailable`), the model list's existing shape, whose object now lives once in `relay.py` and is imported by `app.py`. A failure after a stream has started cannot change the status, so the relay sends a blank line — closing any event the failure cut in half — then that same error object as one `data:` event, then `data: [DONE]`, and ends the body cleanly: the shape the engine itself emits for an error inside a stream at the pin, and the shape the pinned frontend reads. One content-free line names the failure by its exception class alone.

- **The engine client** (`gideon/api/upstream.py`): a second release constant, the completion's 600-second read bound (`exempt:`, from the host's frontend-turn bound by the maintainer's ruling at discovery). httpx's read bound is per network read, so a whole completion — silent until it is finished — would have been cut at the model list's five seconds. The completion call keeps the client's connect, write, and pool bounds and lengthens the read bound alone; the model list keeps its own. The caller owns closing the returned open response.

- **The log** (`gideon/api/app.py`): the request line keeps its fields — method, route template, status, seconds — and gains the two truths the watch makes necessary. The status starts absent rather than 500 and prints as `-` when no response started, so a request whose caller left before any response is no longer logged as a server error; a wrapped `receive` adds the word `disconnected` when the caller left before the response finished, a disconnect arriving after the final body message being the server's own end-of-response signal and not one. An application exception still logs 500. `test_api_service.py`'s existing assertions hold unchanged.

- **The tests**: `tests/test_api_completions.py` (new) drives the application at the ASGI level — a hand-built scope whose `spec_version` the test sets, a `receive` fed from a queue, a `send` awaited one message at a time — over a gated stub engine with the contract stub's surface: the stream's order and per-event flush, the three content-type spellings, the whole and error paths, both disconnects at ASGI `2.3` and `2.4`, the mid-stream failure's events, the two read bounds, and the log's additions. `tests/test_api_relay_sockets.py` (new) is the one real-socket class — a threading stub engine, the real application under a real `uvicorn.Server`, `http.client` reading the chunked body incrementally, all on ephemeral loopback ports: the first event read through the service while the stub still holds the second, and the client's close reaching the stub. Every wait is a bounded event and never a sleep, so a buffering relay fails rather than hangs. `test_service_import_boundary.py` covers the new module with no edit.

- **On the box** (`.scratch/general-turn/assets/02-on-box.txt`, redacted): the apply recreated `gideon-api` alone, as the Window bullet said it would. Criterion 3 — the same request streamed through the service and straight to the engine — passed every gate in both orders: the event kinds in order, the key sets equal by kind, one completion id per stream, the model id equal and equal to the served name, the finish reason and the completion-token count (64) equal, and both streams ending in `[DONE]`. The discovery note's comparison, after one discarded warm-up: the relay costs about one to two milliseconds at the first delta (0.031s and 0.032s through the service against 0.030s to the engine), one recorded comparison and no M-series figure; the one gate is that the first event through the service precedes the engine's own finish at 1.370s, which a buffering relay could not do. Criterion 2 — `vllm:num_requests_running` returned to zero in **0.256s** after an abandoned stream and **0.258s** after a whole completion abandoned during its wait, against a ten-second gate. Criterion 4 — the log over the proof's span carries a line per request with its route, status, and seconds, the two abandoned requests' lines ending in `disconnected` and the whole one's status `-`, and no occurrence of the prompt's sentence, either key, or any caller header value.
