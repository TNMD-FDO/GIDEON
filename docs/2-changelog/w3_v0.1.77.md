## Changes

This release implements slice-0 ticket 20 under the plan `docs/1-plans/clean-vm-full-restore.plan.md`. The acceptance harness gains a second, unattended form, `sudo python3 -m tools.acceptance <ref> --full-restore`. It restores the box's newest complete backup set into a clean no-GPU VM through the runbook's rebuilt-box sequence and proves the receiving-office state recovered end to end (§2.5 item 3). Before this release, no form restored a set into a clean host, and the runbook's §5 had never been run against a real set.

- **The form's table** (`tools/acceptance/run.py`, `FULL_RESTORE_STAGES`):
  - It shares the install run's stages from `preconditions` through `preflight`.
  - The new `set` stage comes second, so a refusal boots nothing. It picks the newest complete set by the product's own staging selection. It requires the box identity's recipient (ADR-0042) to be among the set's manifest recipients, and requires room for four copies of the set under the run directory.
  - Then, in the VM: `apply` → `snapshot` → `stop` → `restore` → `counts` → `decrypt` → `reinstall` → `provision-3` → `apply-2` → `health` → `preflight-2` → `mode` → `users` → `backup` → `audit` → `drill` → `teardown`.
  - The stage functions are in the new `tools/acceptance/fullrestore.py`.
- **The snapshot.** The set, the pgBackRest repository, and a `PushRecord` are placed on the VM's loopback target in the shape `backup push` writes, with the `.partial` rename last. `restore --from target` then fetches the set, re-owns it, and verifies it. The restore session forwards the box's loopback registry into the VM, because the restored rendered tree names the build box's images (the code review's first Major finding).
- **The stack is stopped before the restore.** With the fresh stack running, the restore's pre-restore push refuses against the harness's snapshot: the §3.7 full-copy guard trips, because a fresh stack shares nothing with the snapshot. The form runs the product's `docker compose down` first, so `pre-restore` takes the product's "skipped (stack not running)" path. A real rebuilt box meets the same refusal. The runbook's §5 step 4 now tells the operator to stop the stack first, and the product fix is a new slice-0 ticket.
- **The identity and the plaintext.** The box identity is named by path, and only in two commands: `age-keygen -y` and `age -d -i`. The plaintext secrets tarball goes from the box's `age` through SSH to `tar` in the VM, and never passes through the harness's Python. The VM's own site material is re-installed after the decrypt and before the second apply.
- **The checks:**
  - The two databases' row counts match the manifest's; the only allowed difference is the restore's own audit row, checked by `compare_counts`.
  - Every declared service is healthy, and the applied record names the ref's version.
  - `preflight` passes again.
  - The no-GPU marker is still there, and no engine service is rendered.
  - The set's admin API key lists users at the manifest's count, and only the count is printed.
  - The VM's new full set is sealed first to the restored office recipient.
  - The audit table holds the `restore` row and the `backup_run` rows.
  - `backup drill` passes.
- **Transcripts** are redacted with both the VM's site and the box's.
- **The run directory** moves from `/var/lib/libvirt/images/` to `/data/acceptance/<name>/`. `/data/acceptance` is a new managed `disk-layout` directory (`gideon/host/steps/disk.py`). The teardown row reports the run directory's allocated size, and both forms print an `elapsed:` line.
- **The CLI.** `--full-restore` is the new flag, and the form's default VM is `gideon-acceptance-restore`. `--until` accepts either form's identifiers but refuses the other form's before any host I/O. The dry-run plan names the form.
- **The tag-triggered workflow** runs the form as a second step and uploads both evidence directories. The TRIP-3 `acceptance-run` block runs the form detached after the install run.
- **Tests.** `tests/test_acceptance.py` covers:
  - the form's plan and order, and the `--until` refusal;
  - the `set` refusals, and the identity's absence from every recorded call;
  - the snapshot's argv and record, the `stop` before the restore, and the restore's row checks;
  - the decrypt pipeline and the reinstall order, the users output, and `compare_counts`.

  `tests/test_host_steps.py` adds the managed name. The gate is green: `ruff` and `mypy` (206 files) pass, as do the acceptance, host-steps, backup-push, evidence-hygiene, vendored-skills, and budget tests.
- **Documents.** Updated: the tools leaf, the map (the tools row, `/data/acceptance`, the `acceptance` job, the minor-tag bullet, the operator lines), ADR-0035's amendment, and the glossary's **Acceptance harness** entry. The runbook's §5 changes in two steps:
  - Step 1: the password manager keeps the **old** office identity, because the restore brings the set's recipient back.
  - Step 4: the operator stops the stack before the restore.
  - A new step 6: `host provision` before the apply, so the restored `/data` directories are re-owned.

  Also updated: `on-box-proofs.md` §5, and the box ledger (the `/data` table, §8's acceptance bullet, rules version 2026-09-17.1, and the §12 entry).
- **Ticket 23's last clause** is read from nightly `20260917T060001Z`: two recipients, two X25519 stanzas, and no identity in `files/etc-gideon`.
- **Window**: none. The form applies only inside the throwaway VM. On the box, the one change is the `/data/acceptance` directory, and `apply` recreates nothing.
- **Tutorial**: skipped. This is a patch tag, and the design (a second harness table over the product's own selection and push shape) is recorded in the tools leaf and ADR-0035's amendment.
- **The proof's three reds, fixed under the plan.** The first full-restore run against the tag failed at `snapshot` with `No space left on device`. The loopback target is the `gideon-backup` account's home on the VM's root LV, which was 24 GiB, and the set is 36 GB. The VM's OS disk is now 160 G, with a 128 GiB root LV and the partitions derived from one constant (`tools/acceptance/image.py`). The qcow2 is sparse, so the install run writes no more than before. A test holds the sizing. The second run then failed at the same stage's rename, with `Permission denied`. `vm.run_as_root` puts `sudo` in front of the first command of a script only, so the `mv` chained after the `chown` ran as the CSA account. The two now run as separate root commands, and the snapshot test holds that. The third run passed every stage through `health` and then failed at `preflight-2`: `disk-layout` found `/data/registry` not owned by `gideon`. `restore` re-owns files by the box's numeric ids (`999:983`), which the fresh VM's `gideon` account does not share. By the maintainer's ruling, the form now runs `host provision --no-gpu` (`provision-3`) after `reinstall` and before `apply-2`, which is the fix `preflight` names. The runbook's §5 gains the same step as step 6. The product fix, re-owning by name, is a new slice-0 ticket. The tag was re-made on each fix, and both runs were repeated.
- **Proof**: the plan's to-dos name the install run and the full restore against this tag. Their rows, elapsed times, and disk use are in the evidence commit after this one, under `.scratch/slice-0/assets/20-acceptance-*-v0.1.77/`.
