## Changes

- **The runner joins ADR-0031** (`gideon/host/steps/services.py`; §1.8, §1.5): the box's GitHub Actions runner had been registered without `--disableupdate`, so every poll it made to GitHub's broker carried `disableUpdate=false` and a new runner release would have installed itself — the one component on the box checking for its own updates, and a silent drift from `host.lock`'s `gh_runner` pin. Every registration the `gh-runner` step performs now carries `--disableupdate` and `--replace` (the latter takes over the organization's existing record of the same name — a rebuilt box needs it too), with the registration token in the child's inherited environment as `ACTIONS_RUNNER_INPUT_token` (the runner's own fallback, which registers the value with its secret masker) and never in argv, and the token file consumed on success.
- **The check reads the runner, not the archive**: after the account, group, directory, archive, and `config.sh` probes it reads the installed release from `bin/Runner.Listener.deps.json` (the .NET manifest names the assembly `Runner.Listener/<version>`) against the lock; every settings file present (`.runner` and the server-refreshed `.runner_migrated`, which the listener loads first) as JSON with the runner's byte-order mark stripped, requiring `disableUpdate: true` in each (the key is simply absent when false); and the service by the unit `.service` names through `systemctl is-enabled`/`is-active` — the old `./svc.sh status` probe exited 0 whenever the unit file existed, so a stopped runner read as converged. A registered runner without the flag is `pending-input` naming the token, `pending-input` naming the wait while a `Runner.Worker` process runs, and `drift` only when a token is present and the runner idle.
- **The apply is a real upgrade path and a one-time re-registration**: a new release (archive changed, `config.sh` missing, or installed version behind the lock) is installed as stop → extract → `runsvc.sh` refreshed from the new `bin/` → superseded archives removed → chown → enable → start; a runner registered with updates on is re-registered as stop → `svc.sh uninstall` → `config.sh remove --local` → register → install → enable → start, with the announcement printed once naming the upgrade path from here. The token is resolved before anything stops (the Codex code review's one Major: a release upgrade on an updates-on runner with no token on disk would have stopped the service and never restarted it), and the busy guard runs before every stop. `StepFailure(detail, fix)` (`gideon/host/steps/__init__.py`, rendered by `provision._apply`) lets an apply fail its row with its own fix — the busy refusal and a refused registration are its first users; §1.5's rule that every refusal prints its fix, which the generic "Repair the … apply failure" line did not honour.
- **The documents name the path and the deadline**: the pin watch's `host.gh_runner` pull-request body (`tools/pinwatch/pr.py`) says merge, bring the box's checkout to the merged commit (provision reads `host.lock` from the checkout it runs in), then `host provision`, inside GitHub's thirty-day window for runners with updates off; `.scratch/slice-0/assets/03-office-services-setup.md` §6 carries the token (where, how, one hour), what pauses (the service is down under a minute; a push to `main` queues `mirror-images` until it returns), the upgrade path, the rebuilt-box case, the 2026-09-25 enforcement, and the 404 diagnosis; `10-pin-watch-app-setup.md` §5 gains the Monday bullet. The research note `docs/research/gh-runner-disableupdate.md` (the runner's v2.337.0 source and docs.github.com, cited claim by claim) is merged from its branch — the first note under `docs/research/`.
- **On the box**: the dry run read the live settings file (byte-order mark and all) and reported `would-apply — registered with automatic updates on` over the stale Sep 1 token; the first real run was refused by GitHub with `404 (Not Found)` on `POST /actions/runner-registration` after the local removal — the token had been minted on the repository's runner page, not the organization's — leaving the runner unregistered with its service uninstalled and the row naming a fresh token, the partial state the plan had specified (now a runbook line); with an organization token the next run reported `applied — GitHub runner is registered with updates disabled and active`, then `ok`. `.runner` carries `"disableUpdate": true` (the wire casing the research note could not prove from source, settled by the box and captured as the updates-off fixture; the same runner id kept), the configure trace reads `Env arg 'token': '***'`, `Flag 'disableupdate': 'True'`, `Flag 'replace': 'True'`, the token file is gone, the unit is enabled and active. The ticket's last live criterion — a CI job on the re-registered runner — is this release push's `mirror-images` job.
