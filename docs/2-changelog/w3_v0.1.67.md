# Changelog - Week 3, 16-09-2026, V. 0.1.67

**Release Date**: Week 3, 16-09-2026 at 13:04
**Version**: 0.1.67 (previously 0.1.66)
**Object**: hotfix: v0.1.67 — the turn tests' fake mints fresh chat ids under N

## Changes

- **Issue**: `tests/test_turns.py::TurnHarness::test_concurrent_sessions_overlap_and_record_their_own_chats`, new at `v0.1.66`, failed CI's `checks` job on the release commit `4d442d3` (run 35126591948: `AssertionError: 1 != 0`). The next commit, `eba11a4`, passed on the same code. The harness and the M27 figures are unaffected, because the real frontend gives every chat a unique id.
- **Fix**: under concurrent sessions (a second sign-in), the fake `Frontend` in `tests/test_turns.py` gives chats ids from a counter that never repeats. A single session keeps reusing the lowest free id, which the sequential tests assert (`test_repeat_summary_and_leftover_chats`). The fix was proven by pausing 50 ms after every chat listing to widen the race. Before the fix, the overlap test failed on every attempt (`two@3: refuse — the turn's chat was not found`). After it, the test passed 60 runs out of 60, and all nine concurrent tests passed ten rounds out of ten.
- **Root Cause**: the fake gave each chat the lowest id no stored chat held, although `v0.1.66`'s plan called for a counter that never repeats. Session A listed its chats while session B's first chat was still stored as `chat/1`. B deleted it, A's next turn was stored as `chat/1`, and the finder skipped A's own chat because its id was in A's list from before the turn. On CI's slower runner, a peer's delete sometimes landed inside that window.

**Window**: none. The change is to a test module alone; nothing on the box is applied or recreated. No release note or human read, since this is a pre-General 0.x tag. No acceptance run, since this is a patch tag.
