## Changes

- **The engine's identity, shared** (`gideon/host/render/engine.py`; §20.1, ADR-0009): the service name, the container port, the secret name, and a pure `engine_base_url()` (`http://gideon-generator:8000/v1`) move out of `render/compose.py` into a module both the service and the frontend's connection import, so `render/owui.py` never imports the Compose document builder that imports it. `compose.py`, `apply.py`, and their tests import the identity from its new home; the alias test now holds the profile's served name, the service name, the task model, and the base URL's host to one name.
- **The connection, in the frontend's environment** (`gideon/host/render/owui.py`; §5.2, §15, ADR-0028, ADR-0035, ADR-0017): `owui_environment(inputs, *, engine=True)` renders the connection where the engine is — on a GPU host, and only when the caller asks — as `ENABLE_OPENAI_API=true`, `OPENAI_API_BASE_URLS` (one URL), `TASK_MODEL_EXTERNAL` = the selected profile's generator `served_name` (the key the pinned frontend reads for an OpenAI-compatible connection; `TASK_MODEL` is the local-connection key), `ENABLE_TITLE_GENERATION`, `ENABLE_TAGS_GENERATION`, and `ENABLE_SEARCH_QUERY_GENERATION` on, `ENABLE_FOLLOW_UP_GENERATION` and `ENABLE_AUTOCOMPLETE_GENERATION` off (the second a discovery ruling: a task-model call at every typing pause that §15's list does not name; the pinned frontend already defaults it off, so the value pins the fact), and — on a proxied site — `gideon-generator` appended to `NO_PROXY`, because the frontend's HTTP client reads the proxy variables unconditionally. No `OPENAI_API_CONFIGS`: its absence is what keeps every chat turn on `/chat/completions` (the Responses API is a per-connection `api_type` that document would carry) and the model discovery real (`model_ids` would fabricate the list before the engine can answer). No sampling key; with no preset the connection carries no override ([10] item 15). A test holds the keys added over the previous environment exactly.
- **The key, in the env file** (`render/owui.py`, `render/command.py` unchanged; §1.7, §16): `OWUI_SECRET_NAMES` gains `engine_api_key`, read through the existing loop (a missing file names `apply`), and `owui_secret_environment` emits `OPENAI_API_KEYS=<value>` on a GPU host only, paired with the base URL by index — never into `compose.yaml`. The env file stays 0600, flagged `secret`, never printed by `render --diff`, outside every backup set. Consequence: the frontend is the key's second consumer and the env file a rendered artifact it owns, so removing the key and running `apply` re-renders the file and recreates the frontend through the recreate rule; the engine alone still needs the by-hand force-recreate (the runbook's rotation step now says so; ticket 24 carries the note).
- **The no-GPU host and the drill stay disconnected** (`render/owui.py`, `render/drill.py`; ADR-0035): the marker keeps `ENABLE_OPENAI_API=false`, none of the connection keys, and no key line, so the `no-gpu` fixture is byte-identical; the drill's frontend is rendered with `engine=False` — its project has no engine and must never send load to the production one by name.
- **Proven on the box** (`.scratch/slice-1/assets/05-on-box.txt`): `render --diff` showed the connection keys and the env file as changed without contents; the first apply recreated `open-webui` (the owner of both files) and verified with the engine untouched (`engine healthy 10 s after start`, nothing restarted); the second apply recreated nothing. As the break-glass admin through the ingress (the password and the session token by file and stdin only): the model list named `gideon-generator`; with the engine stopped, the frontend kept its last list, logged one failed fetch, and needed no restart when the engine returned — healthy 57 s after a plain `compose start` of the kept container, against 185 s for ticket 04's recreate; a plain streaming turn answered 270 SSE lines in three seconds — 106 `reasoning` deltas, then 26 content deltas, the last reasoning delta at line 213 and the first content at 215, no `<think>` text; a turn the frontend's completion route manages itself (`parent_id: null` and a `user_message`) created the chat record, generated the title (Motion To Suppress, not the first-message fallback) at creation in parallel with the answer, generated one tag after the reply, and stored the reasoning as an `output` item of type `reasoning` (duration 2 s) beside a `content` that is the answer alone; the follow-up task asked for directly answered "Follow-up generation is disabled" with no engine call; the engine's access log for the turn holds exactly three calls (answer, title, tags); the sentinel reached neither journal nor the frontend's audit file (§19.4); the key's value is absent from `compose.yaml` and from every frontend process's argv, present once in the 0600 env file and — the nature of §1.7's exception, as for the LDAP and database passwords — in the container's environment. The proof's chats were deleted from the admin's history.
- **Research note**: `docs/research/owui-engine-connection.md` (branch `research/owui-engine-connection`, merged here) — the Open WebUI v0.11.3 facts the connection depends on, each cited to the tagged source: the four connection keys and their persistence, the per-connection `api_type` and `model_ids`, model discovery on demand, `TASK_MODEL_EXTERNAL` and the task toggles' defaults (autocomplete already off at this tag), what a task call sends (the title's 1000-token cap, nothing that suppresses thinking, the first-message fallback), the stream handler reading `reasoning_content`, `reasoning`, or `thinking` into a structured reasoning item the client renders with its own collapsible component, the outlet Filter's content built without the reasoning items, `trust_env=True` on every session, and a request shape that carries no sampling override without a preset — plus the box's observation that the frontend keeps its last model list across a failed fetch.
