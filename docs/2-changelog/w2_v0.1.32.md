## Changes

- **The tool** (`tools/tracker.py`; `python3 -m tools.tracker [--root DIR] [--today YYYY-MM-DD] [--strict]`; standard library alone, held by an AST check; the dev venv in the primary at the outstanding-items step, any checkout by hand; never a `gideon` command): the root is `--root` or the checkout holding the module; an effort is every directory under `.scratch/` with an `issues/` subdirectory, a ticket every `NN-<slug>.md` in it, read once — the number from the file name, the title from `# NN: …` or `# NN — …`, the `Status:`, `Blocked by:`, and optional `Tag:` lines bold or plain; `.scratch/CYCLES.md`, `.scratch/BOARD.md`, an effort's `99-observations.md`, `spec.md`, `map.md`, `brief.md`, and `assets/` are never read. A file with no `Status:` line is open with the status `missing` and a finding; a file with no `Blocked by:` line reads as `none`.
- **The blocker grammar** (`parse_blockers`): the line's text with every parenthesised span removed, cut at the end of its first sentence, is what the tool reads; a first word of `none` or `nothing` in any case, an em dash, or a hyphen means no blockers whatever follows; otherwise the sentence splits at semicolons into clauses, each yielding references — a bare two-digit number not adjacent to a digit, a dot, or a hyphen (so `v0.1.12`, `1.0`, and a date never match) meaning the same effort, `<effort> ticket NN`, `<effort> tickets NN and NN`, `ticket NN`, a range `NN–NN` — and a clause yielding none is an **external blocker** kept beside the references, so `the maintainer's ruling …; slice-1 ticket 24 …` is one reference plus an external blocker and a ticket is blocked while any reference is open or any clause is external. The convention that makes this the right reading is written in `issue-tracker.md`: the first sentence lists the blockers, one per clause; an explanation goes in a parenthesis or a second sentence. One line in the tracker is written against it (slice-0 ticket 14's second clause), read as external until its line is rewritten — which the lint asks for anyway, both its references having resolved.
- **Git facts, optional** (`read_git_facts`): two subprocesses through `git -C <root>` — a `log` over `.scratch/` in name-status form with rename detection and short author dates, replayed oldest-first so an add sets a path's opened date and a rename carries it (workflow ticket 04 will move six files), and a porcelain `status` naming the modified and untracked paths. Any failure — no `git`, not a repository, a non-zero exit — leaves the facts absent: the header says so, every age is blank, and the uncommitted-claim rule reports itself unchecked. `build_board` takes a `facts_reader` seam so the suite supplies facts for a fixture that is not a repository; the command always reads git.
- **The vocabulary** (`read_vocabulary`): the one `Statuses: <open statuses>; closed: <closing statuses>` line in `docs/agents/issue-tracker.md`, its order the listing's order; a missing, duplicated, or malformed line is a refusal before any ticket is read, naming the line to add.
- **The lint** (`_lint`), each finding with the ticket's path, line, problem, and fix: an open ticket's reference to a ticket file that does not exist; any ticket's status outside the vocabulary, a missing line included; an open ticket's reference to a ticket already closed (the fix the tracker's own convention: the resolved blocker named in a parenthesis with its tag, or `none`); a `claimed` ticket whose file is modified or untracked (rule 4, checked only with git facts). Rules 1 and 3 read open tickets alone — a closed ticket's line is history. Two shape guards join them: a file under `issues/` outside the name shape, and a blocking cycle among open tickets, whose tickets are listed while the ordering still completes.
- **The sections** (`build_board`, `board_sections`, `listing_sections`): the open tickets carrying a `Tag:` line are the release tickets and the lowest version is the next tag; the **critical path** is that ticket's open transitive blockers — closed and dangling references dropped, each the lint's finding on its own ticket — ordered so every row comes after the open tickets it is blocked by (Kahn's order, ties by effort then number), the release ticket named in the heading (`Critical path to v0.2.0 — slice-1 ticket 18`) and never a row, even through a cycle back to it (the code review's one finding); the **frontier** is open `ready-for-agent` with every reference closed and no external clause, by effort then number, a mark on each on the critical path; **decisions owed** are `ready-for-human` oldest first, unknown dates last; **triage owed** are `needs-triage` older than `TRIAGE_THRESHOLD_DAYS` (7, a starting value the tracker document states and a test holds the constant to); **open by effort** lists every open ticket grouped by effort in name order, within an effort by the vocabulary's order then number, an unknown status last. Every row is number, title, status, blockers (references with a closed one struck through, `external`, or `none`), and age in days; the four cross-effort sections qualify each number with its effort.
- **Two renderers, one model** (`render_markdown`, `render_html`): both iterate the same `Section` and `Row` values, so the two files cannot disagree. The Markdown file carries a header (the generating command, the date, `N open across M efforts (T tickets read in E efforts)`, the git-facts line), the findings as a list, then headed tables. The page is one self-contained file: an inline style with colour tokens defined once on `:root` and redefined under `prefers-color-scheme: dark`, status shown as text and never by colour alone, one table per section and per effort, each row's number a relative link from `.scratch/` to the ticket file, every text escaped, no script, no `<link>`, no `src=`, no absolute URL. Both files are written through sibling temporary files moved into place, so a refusal writes neither; two runs over one tree, one set of facts, and one date are byte-identical in both.
- **The CLI**: `--root DIR`, `--today YYYY-MM-DD` (the tests' and the proof's seam; the default is the machine's local date), `--strict`; a run writes `.scratch/BOARD.md` and `.scratch/BOARD.html`, prints the findings and the summary line to stdout, and exits 0; `--strict` exits 1 on findings; the refusals — no effort with an `issues/` directory under the root, the vocabulary line missing or malformed, a board or page that cannot be written — print `python3 -m tools.tracker: <problem> Fix: <fix>` on stderr, exit 1, and write nothing. The discovery's ruling: the lint prints and never gates; `--strict` is for whoever wants a gate later.
