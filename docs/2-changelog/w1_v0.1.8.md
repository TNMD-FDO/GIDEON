## Changes

- **The decision** (ticket 26; §5.3, §15, ADR-0006): a browser turn on the bare `gideon-generator` failed at `v0.1.7` because the pinned frontend attaches its built-in tools (`time`, `ask_user` — ungated for every role) to every UI turn on a model whose record does not set `capabilities.builtin_tools: false`, and the pinned engine, with no tool-call parser, refuses the resulting `tool_choice: auto` with a `400`. The way out is a model record for the base model, not engine flags: `--enable-auto-tool-choice --tool-call-parser hermes` would make the built-in tools *work*, and `calculate_timestamp` is date arithmetic by a model-called tool — ADR-0006's tier 3, "none in v1" — while `ask_user` and the knowledge tools open surfaces §15 turns off. The frontend never sets `tool_choice` itself; the refused `auto` is the engine's own default. API-only was refused as a resting state: it leaves the admin's browser path broken.
- **The record, rendered** (`gideon/host/render/owui.py`; §3.5, §15, ADR-0009, ADR-0017, ADR-0028, ADR-0035): `base_model_record` builds the base model's own row — `id` and `name` the profile's generator `served_name` (the one stable name, ADR-0009), `base_model_id` null (it annotates the discovered model; it is not a preset), `meta.capabilities` = `BASE_MODEL_CAPABILITIES` (§15's eight toggles off, web search included, plus `terminal`, a capability the pinned frontend added after the spec's list that attaches tools the same way — a toggle §15's list does not carry, recorded on the ticket as ticket 05 recorded autocomplete off; the display-only `citations`, `status_updates`, and `usage` deliberately absent, at the frontend's defaults), `params` empty (no sampling override, [10] item 15), `access_grants` empty, `is_active` true, and the three row fields the pinned sync form requires but overwrites or ignores as release constants (`user_id` = the break-glass username, `created_at` = 0, `updated_at` = 0 — a clock would break the byte-stable render). `ApplyManifestArtifact` emits it as the manifest's one model on a GPU host only: the record belongs to the connection, which follows the engine as the engine follows the no-GPU marker, so the `no-gpu` fixture is byte-identical and the acceptance VM pushes nothing new. The generator lookup and its `models.lock` refusal are shared with `owui_environment`.
- **The removal report complete, and every sync read back** (`gideon/host/owui.py`): the pinned frontend's paged model listing (`/api/v1/models/list`) returns preset rows only; base-model rows live on `GET /api/v1/models/base` (admin-only, unpaged), so `bootstrap` now lists both — `_listed_models` — before the sync and reports a base row the manifest does not name. And because the pinned sync routes catch every persistence exception and answer HTTP 200 with an empty list, a 2xx proves nothing: after each sync `bootstrap` lists again (`_read_back`) and refuses on the sync's step with the logs fix unless the ids equal the manifest's and, per model row, the manifest-owned fields equal the manifest's under `_model_difference` — `params` and `meta.capabilities` as whole mappings, every other `meta` key equal where the manifest carries it and absent or null where it does not (the row model materializes `profile_image_url`, `description`, and `knowledge` as null), grants as `(principal_type, principal_id, permission)` triples, `user_id`, `updated_at`, and `created_at` never compared. The problem text names the id and the field, never a value. Functions are held by id set until ticket 09 pushes one.
- **Visibility, unchanged and understood** (ticket 08's decision, on this same record): the record carries no grant, which under the rendered flags (`BYPASS_ADMIN_ACCESS_CONTROL=true`, `BYPASS_MODEL_ACCESS_CONTROL` unset) is exactly the visibility a discovered model without a record has — offered to admins, never to a `user`-role account, the source's own comment: "only admins can see unconfigured models". The legacy `access_control` key is no longer a field and a record carrying it is silently ignored; the public shape is an `access_grants` entry `{user, "*", read}` with the placeholder fields the form requires. Ticket 05's two-entry model list was the admin's; 08 verifies a users-group member's list on its own box step.
- **Tests** (`tests/test_render_owui.py`, `tests/test_render.py`, `tests/test_owui.py`, `tests/test_apply.py`, the two GPU render fixtures): the record's shape held exactly and the nine-key capability set held exactly, so no key enters or leaves unnoticed; the no-GPU negative; the missing-generator refusal from the manifest; the engine-service test holding the record's id to the service name; both fakes split their model listings the pinned way and `test_owui.py`'s gains a swallowed-failure mode — a missing row, and same-id rows with a stale toggle, a stale non-empty `params`, an extra capability key, or a non-null extra `meta` key each refuse on the sync step, while null-defaulted `meta` keys are not a mismatch; the Functions missing-row case; the stray-model test adds a base-row stray. Nine new tests; the `no-gpu` fixture unchanged.
- **The contract module, the model half** (`tests/contract/owui_apply_manifest.py`): after the first push the admin key's base listing holds exactly the manifest's record (the manifest-owned fields, `user_id` the server's overwrite, the defaulted `meta` keys null) and the preset listing is empty; the admin session hand-edits the record through the frontend's own update route (`POST /api/v1/models/model/update`, the id in the body) and hand-adds a preset through the create route; the next push reports `removed_models == ("stray_model",)` and the record is exact again; a third push is a no-op (the empty report); the eval identity's `/api/models` is `200` with `{"data": []}` — no engine, so the chat-facing merge returns before reading any row — and its base listing is refused by role.
