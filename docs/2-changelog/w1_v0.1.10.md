## Changes

- **The Filter, one stdlib-only file** (`compose/open-webui/functions/arithmetic_guardrail.py`; §16, ADR-0006, ADR-0028): the arithmetic guardrail — the no-model-arithmetic rule's code enforcement, built as pattern families each with its versioned pattern ids, seed, and refusal text; the deadline family ships first. The file runs inside the frontend's container and is imported by path in the tests, so it imports the standard library only, defines no `Valves` (nothing is tunable) and no `toggle` (a toggleable Filter gets a per-chat switch), carries no `requirements` frontmatter, and never contains the four import prefixes the frontend's rewriter replaces over the whole file. The deadline refusal ([07] item 12) and the session refusal are its constants; the pattern set is version 1.
- **The judge** — three bounded shapes, case-insensitive, every quantifier explicit and the longest match held under K = 150: (i) a deadline lead word (deadline, due date, last day, no later than, on or before, expires, runs out, have until, too late, cutoff, time limit) within 80 characters before a date form (`Month D, YYYY`, `D Month YYYY`, `M/D/YYYY`, `YYYY-MM-DD`), the short leads `due` and `filed by` within 8 (so "due process" and "filed by counsel on …" do not trip), the reverse order needing a linking verb ("June 5, 2027 is the deadline") because a symmetric window trips a realistic control and breaks the ceiling; (ii) a day count only in its remaining forms ("23 days remain", "you have 23 days", "10 days from today", "the deadline is in 10 days"), never a period's length ("within 14 days after entry"); (iii) an affirmation opening a sentence near date/deadline/due date, "deadline is correct" with its sentence scanned from the start and abandoned at a negating word, and the confirmation context — the preceding user message carrying a date and a confirmation ask, the answer opening with an affirmation ("Yes, that's right."). `within` and `after` are deliberately absent from the vocabulary; `timely` trips only as "filed on <date> would be untimely".
- **Every rendered text is judged** — the answer and every text part of every output item, the reasoning block included, since General renders the thinking and the outlet body carries `output` as a deep copy (research note §6); a trip on any text replaces the whole message.
- **The restatement rule, tuned on the box**: the generator's thinking quotes the question ("User asks: '… the deadline as March 2, 2027 …'") and its compliant refusals restate the user's date ("including whether March 2, 2027 is correct"), both computations under the plan's judge. A match whose every date form the user supplied is now skipped only where the construction governs the date: a question form (whether/if, an optional determiner and date noun, the date, then is/was/would be/as and correct/right/a date noun), a refusal verb phrase whose object reaches the date with no clause break and no affirmation within 30 characters after, or, in the thinking only, the user's question inside a paired quotation introduced as the user's words or introduced in the same clause; never a reverse-form match, never beside an affirmation in the 40 characters before or inside the match, and "no" is not a marker ("no later than June 5, 2027" asserts). A date the user did not supply always trips. Codex's code review found and closed four bypasses of the earlier versions (a marker merely nearby, the model's own "I calculated", an apostrophe taken for a quote, two quotations read as one span); each is a unit case in the `Restatement` class.
- **The outlet's contract** (research note §5, §8): `outlet(self, body)` returns the body in every path (an implicit `None` skips the persist and the client event); on a trip it sets `content` to the refusal and `output` to one finished `message` item in the frontend's five-key shape (`type`, an id in the `msg_` form — the existing item's reused — `status` completed, `role`, one `output_text` part), because the persist gate keys on a non-empty differing `output` and the renderer prefers `output` over `content`; a clean body is returned untouched. The judgement runs under a guard and an exception is a trip with the id `guardrail/error@1`, since the pinned frontend's outlet chain fails open; `record_trip(trip, body)` runs after the replacement under its own guard, a no-op ticket 11 fills.
- **The inlet gate** (a plan-review finding, verified on the source and ruled by the user): the outlet's replacement reaches a browser turn only — a non-streaming API response is built before the outlet's return is read, a streaming one relayed before the outlet runs — and the route accepts a signed-in user's session token, so `inlet` refuses a user-role request carrying neither a session id nor a chat id (the hand-made request's natural shape; a browser turn always carries a chat id) with "GIDEON answers only through its chat window. Open a chat and ask there.", which the inlet chain surfaces as a `400`. Admins pass; the eval identity passes by its email, held equal to the render module's. The inlet judges no content. Residual, recorded: a hand-made request that adds either id passes and receives the unfiltered non-streaming body.
- **The seed** (`eval/seed/guardrails/deadline-trap.yaml`, README beside it): 19 positives (direct, indirect, confirmation, buried, thinking-only, and the forms the reviews and the box produced) each with the pattern id expected to trip, and 28 realistic doctrinal controls carrying dates and deadline words (the statute's period, cases with their years, tolling with a hypothetical's dates, the model's own compliant refusals, a thinking quoting the question); the unit test holds every positive to its id and the tripping controls to the whole-number one-in-twenty ceiling (one trips, control-19). Every text invented; a case is superseded, never edited.
