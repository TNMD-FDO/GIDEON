## Changes

- **No-GPU mode** (`gideon/host/nogpu.py`; spec §2.5, [29] item 12, ADR-0035): `gideon host provision --no-gpu` writes `/etc/gideon/no-gpu` once (absent-only, refused when `/sys/bus/pci` shows an NVIDIA device — a broken driver refuses, never degrades) and every later command reads the marker through one module: provision skips the five `gpu_host_only` steps (`nvidia-driver`, `nvidia-toolkit`, `kvm`, `registry`, `gh-runner`) with `skipped — no-GPU host` rows, refuses `--only` on one naming the marker, and marks them in `--list`; preflight passes those steps as skipped and skips `driver-tested`, the profile check inert; render takes `no_gpu` as an input (`RenderInputs.no_gpu`, recorded in the manifest), gathers facts without `nvidia-smi`, omits the DCGM exporter and its scrape job (`$dcgm_job` in the Prometheus template), and drops the GPU board and the driver-drift rule through `Artifact.applies` — a registered artifact's file the render no longer produces is stale, never foreign, so leaving the mode adds the files back as new; apply's registry and pull stages judge the rendered stack's images (`service_images`), not every lock pin; restore skips the host registry unit on a no-GPU host; the backup set excludes the marker. A GPU host without a driver now refuses render and apply naming both ways out. Grafana's dashboards provider flips `disableDeletion` to false so a board whose file is gone leaves Grafana's database (the boards are release files under desired state). A third render fixture, `tests/fixtures/render/no-gpu/`, is byte-stable like the other two.
- **The plain-registry rule** (`images.is_plain_registry`; [29] item 13): loopback and an address on the libvirt bridge are the two plain-HTTP registries — `parse_registry` derives the scheme from it, so apply's manifest probe passes `--insecure` and the mirror `--dest-tls-verify=false` for the bridge address too; the docker step lists a plain, non-loopback site registry under `insecure-registries` (the box's `daemon.json` is byte-identical, its registry being loopback).
- **The acceptance harness** (`tools/acceptance/`, stdlib + `yaml` + `gideon.host`, root through `sudo` on the box; spec §2.5, §1.9 steps 3–6, §3.6): `python3 -m tools.acceptance <ref> [--name] [--out] [--keep] [--until] [--dry-run]`. One row per stage, exit 0 iff every row is ok, teardown in a `finally` unless `--keep`, `--out` handed back to the sudo caller file by file. `preconditions` (root, the tools, the pinned image's checksum, libvirt's network, the registry on the bridge, the box's site file, the ref, a same-named leftover destroyed only when it carries the harness's metadata and its disks sit under the harness directory — `--name` collisions cannot delete someone's VM; leftover firewall rules swept); `image` (a 40 GiB OS disk built in one guestfish session from the pinned image, read-only: the ESP and `/boot` partitions carried over, the root filesystem copied into `ubuntu-vg/root` beside `docker` and `swap` LVs, grub reinstalled and the initramfs regenerated with dracut through `virt-customize`; a bare mirror of the box's checkout at `/srv/GIDEON.git`, a non-tag ref getting a mirror-only `acceptance-<sha12>` tag; a sparse 2 TiB data disk); `seed` (NoCloud: two sudo accounts with the run's ed25519 key, the `gideon-backup` account); `services` (a throwaway CA — root and two leaves with the strict-X.509 extensions Python 3.13+ demands — bundled with the office root as the VM's `ca.pem`, the site file rendered from the box's, the bind password read from the box's secret file and the run's SMTP password crossing on stdin only, the sink on the bridge with a transient tagged firewall rule); `boot` (define, start, the lease, `cloud-init status --wait`); `clone`, `provision` (`--no-gpu`; `blocked` rows accepted before the site file, none after; `reboot-required` honoured, bounded), `reboot`, `site`, the second `provision`, `authorize` (the VM's backup public key installed on its own backup account), `preflight` (the sink must hold its authenticated STARTTLS message — ticket 07's item (d) live), `install` (`./install.sh` to the URL), `alerts` (Grafana's delivery through the sink), `probe` (the served leaf equal to the run's, from the box), `rehearse` (a `<next patch>-rc.1` tag made in a worktree of the mirror on the box and pushed into the VM's mirror over SSH — the checkout never touched — then `./upgrade.sh <tag>`, `--rollback`, again, again), `restore` (`backup push`, `restore --from target`, `apply`), `verify` (preflight, the applied record and the checkout's `--version` at the base release, the sink's count, every transcript present), `teardown`. Every product command runs as `sudo … 2>&1 | tee` through `bash -o pipefail -c` as one quoted word — no pty, the terminal never the child's stdin — and its transcript reaches the box only through `vm.redact`: the product's own print-once shapes (`apply.PRINT_ONCE_LINE`, `site_dirs.AGE_IDENTITY_LINE`) and any `AGE-SECRET-KEY-1` token replaced by `<redacted>`; `tests/test_evidence_hygiene.py` is the tripwire over every text asset under `.scratch/`.
- **The SMTP sink** (`tools/acceptance/smtpsink.py`): a stdlib STARTTLS + AUTH (PLAIN, LOGIN) receiver in a thread of the harness, AUTH refused before STARTTLS and MAIL refused before AUTH, each accepted message stored with its authenticated user and TLS fact — tested over a loopback socket with `smtplib`.
- **The run at minor tags**: `.github/workflows/acceptance.yml` runs on every pushed `v*.*.0` tag on the box's runner (`registry mirror`, the harness, the transcripts uploaded even on failure); the `acceptance-run` GIDEON block in `TRIP-3-release` runs it against the local tag between the tag and the merge, an evidence commit carrying the transcripts and the ticket's close-out following the release commit. The `gh-runner` step converges the one sudoers line the runner needs (`/etc/sudoers.d/gideon-acceptance`, a candidate validated with `visudo -c -f`, then moved into place at 0440); the `kvm` step's target state gains `guestfs-tools`, `libguestfs-tools`, and `cloud-image-utils`. The workflow's trust boundary is a repository tag ruleset restricting `v*` creation to the CSAs (`03-office-services-setup.md` §6).
- **What the runs found, fixed here** (recorded on ticket 08 and in the runbook's §6): the firewall step's `DOCKER-USER` drops judged every forwarded packet to 443 and 5000 — the VM's NAT egress included — and now name the Docker bridge they forward into (`-o docker0` / `-o br-+`); a fresh cloud image ships empty apt lists, so `steps.apt_install` refreshes before every install; Python 3.13+'s strict chain verification refused a CA without key usage; apply pulled and verified every lock pin while Compose pulls only rendered services; the restore's `verify` refused an empty root (`sha256sum -c` refuses an empty list) and now walks every snapshotted root exactly — any path the manifest never inventoried refuses before anything live stops; after two promotions a restore followed the cluster's current timeline, so every set restore now names its own backup (`--set`), that backup's timeline (`--target-timeline`, read from `pgbackrest info`'s archive start, over a stopped stack through the one-off container), and its target (`--type=time` to `--at` or the set's boundary) — the third timeline lesson after `v0.0.27`'s two. A provision step's failed apply now shows the failed command's own stderr instead of `CalledProcessError`.
