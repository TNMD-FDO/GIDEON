**Version**: 0.1.6 (previously 0.1.5)

## Changes

- **The pin** (`images.lock`; spec §5.2, §2.4, ADR-0031): `vllm-openai` is the tenth mirrored pin — `docker.io/vllm/vllm-openai:v0.27.1` and the multi-platform index digest `skopeo inspect` resolved on the box on 2026-09-04. `registry mirror` copied it whole (`--all` keeps the pinned digest true: about 9.1 GB for amd64 and 10.5 GB for arm64 compressed; `/data/registry` is 33 GB after it), the pin watch judges it by the same-shape rule like every other image, and the lock's comment says a bump is completed only by the engine coming up healthy on the box and, from slice-1 ticket 12, by `engine verify` (§6.7). `tests/test_images_lock.py`'s pin-name list names it. The Docker Hub hosts the copy traverses were already in the `host-provisioning` egress group.
- **The service, in render** (`gideon/host/render/compose.py`; §5.2–5.3, §1.3, §5.4, §20.1, ADR-0009, ADR-0017): `engine_service` builds `gideon-generator` from the selected profile's `generator` model and the host facts, on a GPU host only (constructed under `not inputs.no_gpu`, never built then deleted, so the UUID lookup never runs over a no-GPU host's empty tuple). `engine_command` is the repository, `--revision` the pinned commit, `--served-model-name` the served name, `--host 0.0.0.0`, `--port 8000`, then every lock flag in lock order with its `--` restored and `true` as a bare flag — nothing else, so §5.3's "not set" block (prefix caching, the mamba cache mode, the chat-template kwargs, any speculative-decoding flag) and vLLM's two opt-in request-logging flags are absent by construction. The environment is the lock's `serve.env` in order, then `VLLM_NO_USAGE_STATS=1` and `DO_NOT_TRACK=1` (release policy, `tests/test_no_self_update.py`'s entry), then `TZ`. The GPU is one CDI device request, `nvidia.com/gpu=<UUID>` at the model's `gpu` index of `nvidia-smi -L`'s order; `/data/models` (`weights.MODELS_ROOT`) is mounted read-only at the profile's `HF_HOME`; no port is published, so only Compose-network peers reach it; the healthcheck is `curl --silent --fail` against `/health` on the loopback port (unauthenticated by vLLM's design, answering only once the engine is built) with `start_period` the readiness bound; no shared-memory setting (one GPU, no parallelism — a source-justified deviation from vLLM's quick-start, `docs/research/vllm-engine-service.md` §7). The refusals name their fix: a profile without a generator model, a GPU index beyond the host's UUIDs (`nvidia-smi -L`, preflight's `hardware-profile` check), a profile env without `HF_HOME`, a missing pin. The service sits after `open-webui`; both GPU fixtures gained it byte-stable and the no-GPU fixture's document is unchanged.
- **The key** (`gideon/host/secrets.py`, `render/compose.py`'s `engine_wrapper`; §1.7, §5.2): `engine_api_key` is the tenth password-kind entry of `SECRET_REGISTRY` — generated absent-only by apply's `secrets` stage, `root:gideon` 0440, never printed — and reaches the engine only through the Compose secret mount at `/run/secrets/engine_api_key` and a fail-closed entrypoint: `sh -c` under `set -eu` refuses to start, naming the file on stderr, when the file is missing or empty, else exports `VLLM_API_KEY` (which vLLM v0.27.1 treats as `--api-key`'s equivalent, note §1) and execs `vllm serve "$@"`, the fourth entrypoint element being `$0` so the command's arguments start at the repository. The key is therefore never in `compose.yaml`, in `docker inspect`'s command or environment, in argv on the host, or in a row; `tests/test_render.py` runs the wrapper under `/bin/sh` with a temporary file and a stub server to prove the export, the absent-file exit, and the empty-file exit. Spec §5.3's `engine-token` path and `--api-key <file:…>` form are met by this file and this mechanism; `models.lock`'s serve comment is corrected (comment only, no value moves).
- **The readiness bound, in apply** (`gideon/host/apply.py`; §3.5, §3.6 step 5, ADR-0017): `ENGINE_READY_SECONDS` = 900 in `render/compose.py` is both the healthcheck's `start_period` and the bound verify waits for the engine. `wait_for_services` takes an `attempts` keyword (restore's store wait and the drill keep the default), `run_apply` records an injectable monotonic clock when the `start` stage returns, and `_verify_stage` waits in two phases when the engine is rendered: every other service under the default sixty-second bound (an unrelated failure names its own logs within a minute), then the engine alone under what remains of the bound counted from the start stage (a floor of one read), then one exact read of the whole set; the ok row carries `engine healthy N s after start`. A no-GPU host keeps the single exact wait.
- **Proven on the box** (`.scratch/slice-1/assets/04-on-box.txt`): `render --diff` showed the one new service with GPU 0's real UUID; the first apply created the key, pulled the image, verified the weights, started the engine, and reported it healthy 185 s after start (the journal: weights loaded in 2.41 s, `init engine … 133.09 s (compilation: 78.66 s)`, `GPU KV cache size: 1,766,022 tokens`, `Maximum concurrency for 262,144 tokens per request: 6.74x`); `VLLM::EngineCore` holds 88,430 MiB on GPU 0 and nothing else of ours is on either GPU; a second apply created and recreated nothing and reported the engine healthy 0 s after start; a streamed Chat Completions request from the frontend's container by service name answered 100 SSE lines from `gideon-generator`, the same request without the key 401, `/health` 200 without one; the prompt's sentinel never reached the journal and the access log carries method, path, and status only; `docker inspect` and the host-visible argv of both `vllm serve` processes hold no key. The first proof had expanded the key into command lines, which the code review caught (sudo journals the expanded line): the key was rotated — removed, regenerated by apply, the engine force-recreated to mount the new file, healthy again in about 200 s — and the proof redone with the key passed only by file (`grep -F -f`) and stdin (a curl config document).
- **Lessons recorded**: two GIDEON blocks in the TRIP-2 skill, listed in `docs/agents/tooling.md` §4 — `on-box-page-cache` (a session's cgroup carries the page cache of every byte its children stream, the harness's memory guard reads it, and `memory.reclaim` empties it before a background Codex run) and `on-box-secret-argv` (an on-box proof passes a secret by file or stdin only); the install runbook gained the engine paragraph and the key-rotation step; `docs/4-unit-tests/TESTING.md` names the second test that shells out.
- **Research note**: `docs/research/vllm-engine-service.md` (branch `research/vllm-engine-service`, merged here) — the vLLM v0.27.1 facts the service depends on, each cited to the tagged source: the key from the environment and the unauthenticated `/health`, the build-before-listen readiness ordering, the image's root process and `curl`, the flag set and defaults, zero writes under `HF_HOME` offline, the usage-statistics switches, shared memory at world size one, the two start-up lines (no separate Gated-DeltaNet line at this tag), the tag on Docker Hub, and request logging off by default.
- **Handoffs**: ticket 05 (the service name and port, the secret and the env-file path for the frontend, the observed `reasoning` delta field and the `[DONE]` stream); ticket 04's notes on the file name, the env form of the key, and the measured first start against the bound.
