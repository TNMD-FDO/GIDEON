## Changes

- **`gideon models pull`** (`gideon/host/weights.py`, `gideon/cli.py`, `gideon/host/cli.py`; spec §5.4, §2.4, §2.3, §20.2): the stub becomes the eighth guarded ordered command. For each model of the selected profile it makes `/data/models/hub/models--<org>--<name>/` hold exactly the pinned files in the Hugging Face hub-cache layout — `blobs/<sha256>` (root-owned, 0444), `snapshots/<revision>/<path>` as depth-correct relative symlinks, `refs/main` the bare commit hash with no newline (what huggingface_hub reads whole), so the engine's default-revision lookup resolves to the pin. Classification over the `Host` seam names every pinned path `present`, `absent`, `partial`, `unlinked` (a blob without its link, or a link elsewhere — relinked, never re-downloaded), or `mismatched`, and a snapshot entry the lock does not name `foreign`; one `sha256sum -c -` pass, the lock's digests on stdin, verifies every blob present, a tool that cannot run refusing rather than turning every blob into a download. The fetch is `wget -c -S` into `blobs/<hex>.partial` (the site's `egress_proxy` by `-e`, `proxy_auth` through the WGETRC file the egress check already uses, never argv), the size by `stat` and the digest by `sha256sum` checked before `mv -f` and `ln -sfn`. Per-file lines print only for what changed (`fetched`, `resumed … from <bytes>`, `refetched`, `relinked`, `removed`, `kept`); the row per model is `fetched`, `present`, or `failed` with its fix: repin-or-republish (§2.4) for a 401/403/404 at the pinned URL or a fresh fetch whose size or digest the lock rejects, the `install-upgrade` group for a host that did not answer, the file to remove for a foreign entry, free space walked in fetch order with a damaged blob's bytes credited at the point it is removed. Every host a fetch traverses — the origin and every `Location:` of `wget -S`'s indented headers — reaches the row and is held to the `install-upgrade` group of the loaded `config/egress.yaml`; a host the group lacks prints `uncovered host <h>: add it to the install-upgrade group of config/egress.yaml`, visible and never a refusal.
- **A damaged blob converges** (discovery ruling 4): a present blob whose size or digest mismatches the lock is re-fetched and reported (`refetched <path>: on-disk digest mismatched the lock`) — the tree is derived state and the pull converges it the way provision converges the host; refusal is kept for what cannot converge, the foreign entry and the upstream that no longer matches.
- **The pull record and the prune** (`/data/models/gideon/pulls.yaml`, beside the hub and outside it; the Codex plan review's reshaping of ruling 6): four slots — `in_progress` (the claim: profile, the model set as repository-plus-revision references, the start time, and the process identity), `current`, `previous` (the last complete set whose references differ), `retiring` — walked in five atomic whole-file writes: claim (an alive claim refuses — alive means the recorded pid exists with the same kernel boot id and `/proc/<pid>/stat` start time, so a reboot or a reused pid never blocks; a dead claim with this run's set is resumed, one with another set has its references not named by `current`, `previous`, or the claim journaled into `retiring` in the same write), prune then clear, converge, rotate (the claim to `current`, the old `current` to `previous` when it differs, the old `previous`'s unnamed references to `retiring`), prune then release. One rule governs every write — `retiring` holds exactly the references that leave the named slots — so a rollback from B to A retires nothing of A, an interrupted verify of the current set never retires it, and a bump that moves one model of two retires one reference. The prune removes retiring snapshots (each path first held below its repository's `snapshots/`), then every blob and stray `.partial` that no snapshot still on disk references — recorded or not, so a hand-pulled revision keeps its blobs — and a repository left without a snapshot; the running claim's own digests are never removed, so an interrupted download's partial survives a prune. The record's values are held to the lock's `ROLE_NAME`, `HF_REPO`, and `REVISION` grammars on read (the code review's Critical), a malformed file refusing with a fix that says what removing it forgets.
- **Apply's `models` stage** (`gideon/host/apply.py`; §3.6 step 5): thirteen stages — between `pull` and `recreate`, the stage loads `config/egress.yaml` from the checkout and runs the same `pull_profile` over the rendered inputs' site and profile; the pull's per-file lines and per-model rows print first, then one `models` row (`1 model(s) present` / `fetched`; `; uncovered: <hosts>` when any); a failed pull, or one that raises, is one refuse row before anything restarts. `run_apply` gains `egress_path` and the injectable `pull_models` seam. Install and upgrade inherit the stage: a pin bump pulls the new revision inside the upgrade's apply before the engine restarts, and `upgrade --rollback` re-applies a set the record kept. The stage runs on a no-GPU host too (ruling 2: the marker governs serving, ADR-0035; greenfield issue 29 item 13 wants the VM's download for real).
- **The shared wget proxy shape** (`gideon/host/steps/__init__.py`, `gideon/host/checks/network.py`): `wget_argv_for_site` and the `temporary_wgetrc` context manager (the 0600 file under `/run/`, the `env WGETRC=` prefix, removal on every exit path, the caller's command in the refusal's fix) serve the egress probe and the pull; the probe's argv and rows are unchanged.
- **The allowlist** (`config/egress.yaml`, version 7; `tests/test_egress_allowlist.py`): the real pull on the box was redirected to `us.aws.cdn.hf.co`, which the `install-upgrade` group did not name — the pull's `uncovered host` line said so — and the host is added with a plain probe (it answers 200 unsigned); the VM's install then fetched all 80 files via `huggingface.co` and that host with nothing uncovered, and its preflight probed the new entry.
- **The harness's install budget** (`tools/acceptance/run.py`): `_INSTALL_TIMEOUT_SECONDS` 1800 → 3600 for the download inside install's apply; the VM's install took under fifteen minutes.
