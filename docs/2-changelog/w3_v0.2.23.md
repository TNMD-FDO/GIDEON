# Changelog - Week 3, 20-09-2026, V. 0.2.23

**Release Date**: Week 3, 20-09-2026 at 19:57
**Version**: 0.2.23 (previously 0.2.22)
**Object**: hotfix: v0.2.23 — the pin watch completes a shallow checkout

## Changes

- **Issue**: the pin watch reported the first live Matt Pocock proposal, pull request 5 (`pin-watch/skills.matt-pocock`, `6654f6b` → `3cca18b`, opened 2026-09-07), as `completed — 46be265` on every run from 2026-09-08 on — runs 34249932475, 34389091105, 34878603210, and 35395493135 — though `46be265` is the watch's own commit and no person had committed to the branch. A `completed` branch is one the watch never pushes to again, so the proposal was never refreshed: by 2026-09-18 upstream stood at `c55ee46` while the pull request still proposed `3cca18b`, its body still pointing at `docs/agents/tooling.md` §6, since renumbered §3. The same rule guards a flagged `models.lock` proposal.
- **Fix**: `sync()` in `tools/pinwatch/pr.py` asks `git rev-parse --is-shallow-repository` and, when the checkout is shallow, makes its one fetch `--unshallow`, before any branch is judged. The rule now holds wherever the watch runs and rests on no line of `pin-watch.yml`, which no test reads. `tests/test_pinwatch.py`: the call-order contract gains the read as its first call (the push sequence's slice moves one position, the same seven commands); `test_shallow_checkout_is_completed_by_the_one_fetch` holds the `--unshallow` argv, and `test_unreadable_shallow_state_refuses_before_the_fetch` holds that a failed read refuses with no fetch made.
- **Root Cause**: `branch_state` protects a person's work by counting `git rev-list --count origin/main..origin/<branch>` above one, and that count is true only over a whole history. `actions/checkout` clones at depth 1 by default, so `origin/main` is a cut tip: once `main` moved past the branch's base, nothing the clone held connected the branch's parent to `main`, and the count became the branch's entire fetched ancestry. The contract tests could not see it — their fake `Host` answers the count with the number the test supplies — and both dry runs before the proposal opened listed the pin `current`, where no branch exists to count.

**Reproduced and verified on the record.** Counted by hand first: 249 in a depth-1 clone of `main` against 1 in the full clone. Then the watch itself, `python3 -m tools.pinwatch --dry-run --only skills.matt-pocock --root <clone>`, against a fresh depth-1 clone each time. Before the fix, the hosted runner's own row: `skills.matt-pocock: completed — 46be265849fa0f1ad5b9097099f612bcce5dd67e; upstream now c55ee46`. After it: `skills.matt-pocock: would updated — 6654f6b → c55ee46 (proposal) — PR …/pull/5` (the row's address shortened here), the clone then answering `false` to `--is-shallow-repository` and the count 1. The gate: `green in 318.4s (ruff, mypy, pytest; all cases)`. The hosted proof is the next run of `pin-watch.yml`, whose row for this pin should read `updated`.

**Window**: none. No rendered file, pin, Compose block, or secret moves; the change is in the pin watch, which runs on a hosted runner and touches nothing on the box. Nothing is applied and nothing users see is recreated.

**Release note**: `docs/release-notes/v0.2.23.md`. Nothing user-visible — a fix to repository tooling.

**The human read** (ADR-0036, ADR-0044): does not apply. This is a patch tag before go-live, and the diff touches no path carrying user text or a refusal.

**Lesson, folded where it belongs**: ADR-0033 carries an amendment — the consequence that a person's branch is left alone rested on a count that a shallow history falsifies, failing safe for a person's work and silently for an untouched proposal — which is the comment standing ticket 19's criterion names for a corrected assumption; `docs/archi/tools.md`'s pin-watch invariants now say the one fetch completes a shallow checkout first. Standing ticket 19 stays open: it waits on the pull request's merge, and a `completed` row written before this release proves nothing.
