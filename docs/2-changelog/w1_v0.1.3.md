## Changes

- **The template** (`docs/release-notes/TEMPLATE.md`; spec §21, §2.2): version 1 of the release note every user-facing tag ships from `v0.2.0`, a release artifact under `docs/`. Its `## ` headings outside HTML comments are the required sections — **What is new**, **Coverage**, **Next maintenance window** — under the tag title `# GIDEON v<x.y.z>` and a `Template: 1` line every note repeats, so a later template never falsifies an older note. The authoring guidance lives in HTML comments a written note drops: the audience (every user and a receiving office's CSA), no user, matter, or office-specific text, the coverage line copied from its source (the fixed pre-launch sentence until go-live, the Research preset's regenerated description after), the window rule, and the optional **Rules of use** section carrying §21's practice rule verbatim — *Nothing from General goes into a court filing unchecked, and until go-live there is no Research to check it in.* — which the pre-launch note (ticket 18) copies. The "what was bumped" section is template version 2, generated from the locks' history by slice-0 ticket 14, never typed.
- **The test** (`tests/test_release_notes.py`; §21): the template declares the newest version and exactly its headings (a heading change without a version bump is red); every `docs/release-notes/v*.md` names a SemVer tag in its file name, a matching title, a known template version, that version's headings in order with text beneath each, no authoring comment or `<…>` placeholder, and the practice rule verbatim wherever the optional section appears; from `__version__` `0.2.0` a note for the current version must exist — every tag from General ships one, a release with nothing user-visible says so, and the CSAs decide whether to send it. Every finding ends in its fix (the template to copy, the path to write, the heading to add), which is also what a hotfix session reads when its test run goes red, so `TRIP-hotfix` needs no block of its own. Five tests, twelve sub-tests.
- **Two documents, two audiences** (§2.1, §21): the changelog under `docs/2-changelog/` stays the engineering record and the one `gideon upgrade <tag>` reads for its `## Breaking` section; the release note is the user-facing artifact the CSAs send and a receiving office reads. `upgrade.py`'s fallback line now says the changelog names none (one constant, `_NO_BREAKING`, in place of seven literals), the install/upgrade runbook's `version` row says the changelog, and its §2 gains a "Before a user-facing tag" paragraph (the note, who sends it, the supervisor, the window), leaving the quiet- and maintenance-window rules to ticket 18.
- **The release skill** (`.claude/skills/TRIP-3-release/SKILL.md`, inside the existing GIDEON markers only; `docs/agents/tooling.md` §4 rows updated, origin `v0.1.3`): the `user-facing-tag-check` block writes the note from the template, runs the test before the commit question, and keeps the human items (the supervisor informed ≥ 1 working day ahead, the deploy in an announced maintenance window, the CSAs sending the note, the bootstrap ticket 01 gate); the `breaking-section` block says a major release's *changelog* carries `## Breaking` and that the note never does.

The leaf reaches the box as the `USER_PERMISSIONS_WORKSPACE_KNOWLEDGE_ACCESS` default in `compose.yaml` and as every group's manifest permissions; the nine render fixture files moved by that leaf and the two hashes that follow it, and `tests/test_render_owui.py`'s assertion flipped, citing §21 and the lift so slice 6 meets the contract that flips back.
