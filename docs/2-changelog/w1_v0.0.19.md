## Changes

- **The host follows the site file** (`gideon/host/steps/timezone.py`; Appendix C, §1.5): a nineteenth provision step, `timezone`, registered after `time-sync`. It reads `office.timezone` (already validated as an IANA name against the host's own zoneinfo database), checks the host with `timedatectl show -p Timezone --value` — `converged` on a match, `drift` naming both zones with `timedatectl set-timezone <zone>` as the fix, `unfixable` naming `systemd-timedated` when the probe fails, `blocked` with the site-file fix until `site.yaml` exists — and applies with `timedatectl set-timezone`. Preflight's Phase A refuses a drifted host zone like any other step. Until now no step set the host clock, so the box ran UTC and every rendered timer fired at its `OnCalendar` hour in UTC: 01:00 UTC is 8 PM Central, inside the office day.
- **Every timer names its clock** (`gideon/host/render/systemd.py`, the three timer templates; §19.6, §3.5): the reconcile (03:00) and backup (01:00) calendars join `DRILL_CALENDAR` as release constants, one helper composes `<calendar> <office.timezone>`, and all three timer templates take `OnCalendar=$calendar` — rendered as `*-*-* 01:00:00 America/Chicago` for TNMD and `America/Denver` for the second fixture office. systemd evaluates a calendar expression carrying an IANA zone in that zone, so the unit fires at the office hour whatever the host clock says, and reads correctly once the host clock agrees. Caddy gains `TZ` (Postgres and the frontend already carried it), so Appendix C's "every container" is literal and a contract test now says so; `gideon-backup-drill.service` gains `After=gideon-backup.service`, so a drill can never start while a backup run is active.
- **The switch's one visible side effect, specified per timer** (the plan's §7, from the Codex plan review): a `Persistent=true` timer rebases its next elapse from its recorded last trigger, so when a unit is reloaded with a zoned calendar or the host zone changes, a timer whose first office-zoned occurrence after that trigger is already past fires at once — reproduced with a throwaway user-scope timer on the dev seat before it was written down. For the two daily timers that is every hour except the few between the old UTC instant and the zoned one that follows (their overlap, 03:00 UTC to 01:00 office time, spares both: 10 PM to 1 AM Central in daylight time, 9 PM to 1 AM in standard time); the drill catches up on any day of its interval once it has run, never before its first trigger. Accepted as at most one run per timer of an idempotent nightly job — stopping the timers around the switch changes nothing, since the stamp is re-read on start, and editing systemd's private stamp files was rejected — with the drill ordered after the backup and the runbook saying what to expect.
- **Documents name the clock**: `config/site.example.yaml`'s `office.timezone` comment (provision sets the host clock to it, every container gets it as `TZ`, every timer's `OnCalendar` carries it — §19.6's schedule is office time); the backup runbook's "when" table says office time and carries the upgrade note; `CONTEXT.md` gains **Office time**; ticket 07's planning note now points at the office-local first runs.
- **On the box** (the ticket's on-box evidence): `host provision` — `timezone: applied — host timezone is America/Chicago`, then 19 ok; at the switch (19:13:06 CDT) the reconcile caught up once with one correction, the backup and the drill did not (their stamps are their start time), exactly as predicted; `apply` rendered 11 files, recreated Caddy with `TZ=America/Chicago`, re-enabled the three timers; `systemctl list-timers 'gideon-*'` shows Thu 01:00 CDT, Thu 03:00 CDT, Sat 04:00 CDT, and `systemd-analyze calendar` agrees on every rendered expression; `preflight` 31 checks, 28 pass, 3 inert, exit 0. No defect surfaced.
