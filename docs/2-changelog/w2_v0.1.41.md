## Changes

- **The model pin** (`tools/pinwatch/hub.py`, `pins.py`): one `ModelPin` per model a hardware profile in `models.lock` pins, between the host pins and the skill pins in the registry, `models.<role>` for the reference profile's models and `models.<profile>.<role>` for another profile's. `resolve` reads the Hub repository's default-branch head with one request (`GET /api/models/{repo}`, the `sha`) and is `current` when it equals the pinned revision; otherwise it lists the tree at the head (`GET …/tree/{revision}?recursive=true`, every `Link: rel="next"` page followed, file entries alone, a leading-dot path skipped, a path outside the lock's grammar refused), takes each LFS file's digest from the listing (`lfs.oid`) and downloads and hashes each other file through `resolve/`, its length held to the listing's size, and returns a bump whose one scalar change is the revision and whose one block is the regenerated `files` mapping in sorted path order. The bump is a proposal when the role's total pinned bytes change and a memory row of the same profile names the role (§7.6). The Hub answers a gated, private, or absent repository with 401 to the anonymous watch, and the anonymous limits' 429, each one failed row with the URL to check; the facts are `docs/research/hf-hub-model-api-pin-watch.md`.
- **Blocks in the patcher** (`patch.py`): `Bump.blocks` carries a key path with its loaded mapping before and after; `apply_bump` anchors each block's old mapping against the lock as it anchors a scalar, replaces the scalars through `replace_scalar` and each block through `replace_block` (the block's lines rendered by `hub.render_files_block` at the key's indentation plus two, a key quoted only when its plain form would not load back as the same string), and the reload-and-compare guard proves nothing but the revision and the block moved. One `_key_lines` walk serves both replacements. `python3 -m tools.pinwatch.hub <repo> [<revision>]` prints a repository's `files:` block by hand — the tool slice-1 ticket 23's candidate blocks will be produced with.
- **The lifecycle** (`pr.py`, `cli.py`): `models.lock` is a product lock, so a model branch carries the render fixtures regenerated (every fixture manifest embeds `models_lock_sha256`); a revision title shortens both hashes to twelve characters; the body's table carries the block as file counts and total bytes, the "what merging does" paragraph says nothing moves on a box until its next `apply` and only on a box whose site file selects the pin's profile, where the `models` stage fetches the files and recreates the engine in a maintenance window from `v0.2.0` (§21), and a proposal's paragraph names the role, the two totals, and each memory row naming the role with its `gb`, telling the person to re-judge the row per §7.6 on the branch, regenerate the fixtures, and commit both; a person's commit on a `pin-watch/models.*` branch completes the proposal and the watch never pushes over it, its row naming a newer upstream revision when one appears (ADR-0033's rule extended from the skill records); the carries check compares blocks beside scalars, so a branch holding the new revision over a stale block does not read as carrying the bump. The watch reads `models.lock` from `origin/main` like its other records, and `python3 -m tools.pinwatch.notes` lists `models.<role>` as watched, the research notes' existing ids joining the bump body's re-verification list with no rename.
