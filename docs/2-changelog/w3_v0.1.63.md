## Changes

The search sentinel's stub answered first and logged second. `tests/test_sentinel_stub.py`'s `request` helper enters `contextlib.redirect_stdout`, makes one loopback request, reads the whole response, closes the connection, and leaves the redirect — while the stub's handler wrote its content-free request line from the server thread only after the response bytes were flushed. Nothing ordered that write before the redirect's restore, so on the hosted runner of `v0.1.55`'s `checks` run (34563026176) the restore won and `test_request_line_is_content_free_and_marks_only_matching_q` failed on `'' != 'GET /json status=200 sentinel=no'`; five of five local runs and the re-run were green, and the release had not touched the stub since `v0.1.35` (slice-1 ticket 77; §15, §18.2, §2.6). This release reverses the order and then holds it. Test material only: nothing under `gideon/`, `compose/`, or `config/` moves. The plan is `docs/1-plans/sentinel-stub-test-log-read-races-the-server.plan.md`.

- **The stub logs before it answers** (`tests/contract/sentinel/stub.py`): `_send_logged` calls `_log_request` and then `_send`; `_stream_completion` calls `_log_request` with status 200 before its `send_response` and drops the trailing call after the flush. Those two methods carry every response path — the GET routes, the unknown-path 404, the POST's 400 and 404, the non-streamed completion, and the streamed one — and the status is already a parameter in every call, so the line's text is unchanged: `<method> <route> status=<status> sentinel=<yes|no>`, never the query string. **The mechanism is a happens-before chain, not a bound**: the client cannot read a response the server has not begun, so the loopback socket itself orders the write before the read. No wait, no sleep, no poll — `docs/4-unit-tests/TESTING.md`'s rule that no test ever sleeps or waits for real is kept, which is why the helper's bounded poll was declined at discovery. The module docstring gains the one sentence naming why the order is load-bearing, in the file that carries the reliance.
- **The tripwire** (`tests/test_sentinel_stub.py`): a module-level `RecordingStubHandler` subclasses the stub's handler and overrides `send_response` alone — the one method both `_send` and `_stream_completion` call first, and which only buffers the status line until `end_headers` — recording what the current `sys.stdout` holds at that instant when the stream offers `getvalue`, and a marker otherwise. `setUpClass` serves through it, `setUp` clears the record to the marker so a stale record can never satisfy the assertion, and one new test, `test_request_line_is_written_before_the_response`, makes a plain GET (`/health`) and a streamed POST (`/v1/chat/completions`) and asserts for each that the record taken at the response's start already equals the whole line the helper returned and ends in a newline. With the order right that is true on every run; with the order wrong the record is empty on every run — **a reorder back is red deterministically rather than a rare hosted flake**. The subclass adds no route and changes no line, so the stub's shape is untouched; `StandardLibraryOnly` is unchanged, no import having been added. The helper keeps its shape, arguments, and four-value return, gaining a docstring that states what it relies on.
- **The second shape, closed too**: a late line landing in the *next* request's buffer — the tests run sequentially and each request opens a fresh redirect — would have failed a `log.strip()` equality with two lines. It was never seen, and it vanishes with the first shape once the line precedes the response.
- **The proof** (`.scratch/slice-1/assets/77-twenty-runs.txt`): a fixed loop script in the session's scratchpad, run as one plain `bash <path>` against the worktree's `.venv`, ran the module twenty consecutive times stopping at the first failure — twenty runs, no failure, each `8 passed, 10 subtests passed` in 0.53 s. The asset holds the twenty summary lines and the date, nothing else. The hosted half of the ticket's first criterion is this release's push: the `checks` job runs the full pytest on `ubuntu-latest`, and the `search-sentinel` job exercises the copied stub on the box's runner as the contract's own confirmation. **The ticket is therefore resolved at the close-out, not in this commit**: the release commit ticks nothing and leaves `Status: claimed`, and the Step 15 tracker commit ticks both criteria, records the hosted run's id, and sets `Status: resolved` — a criterion naming the hosted runner is not ticked before that runner has run.

The stub's image, port, routes, bodies, and line shape are byte-for-byte what the contract copied before.
