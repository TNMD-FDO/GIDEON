### The security policy

`SECURITY.md` at the root, the location GitHub reads first. The route is the public repository's private vulnerability reporting — the Security tab of `github.com/TNMD-FDO/GIDEON`, "Report a vulnerability" on its Advisories page — reaching the repository's administrators, the two CSAs, and nobody else; a vulnerability is never a public issue, a pull request, a chat, or a mailing list. The file names no mailbox: a mailbox is an office value under slice-1 ticket 54's rule, and private vulnerability reporting is a public-repository feature GitHub enables in the repository's settings, so ticket 57's settings gain it by a dated line written at the claim. What a report includes: the tag, the hardware profile or the no-GPU declaration, a reproducer built from synthetic text (a made-up prompt, document, request, and response), sanitized diagnostics (the command and its rows or a log excerpt with every real value replaced), and what the finding lets an attacker do; what it never includes: a site file's values, a secret, or any chat, matter, or client text — spec §0.1 rule 2 binding the reporter as it binds the code. In scope: the `gideon` package and its CLI, the rendered stack (the Compose templates, the Caddyfile, the units, the Filters), the built images, the migrations, the three scripts, the workflows, and GIDEON's exposure to an upstream defect — a pin file naming a vulnerable version, or the rendered configuration exposing a component's defect — reported here as GIDEON's exposure even when the defect itself belongs upstream. Not in scope: an office's own site file and secrets, its directory, network, and hardware, the host beyond what `host provision` sets, and an upstream component's own defect, reported to its project, a fix there reaching GIDEON as a reviewed pin update; the two scopes meet at the pin. What happens next, as text and never a link into the tracker: the CSAs acknowledge the report on the advisory, it becomes a ticket in the development repository's private tracker under the advisory's identifier carrying no detail a public reader could use, the fix ships as a tag every office upgrades to, and the advisory is published with that tag, crediting the reporter unless they decline. No response time is promised (the user's ruling at discovery). Supported versions: the latest tag; before `v1.0.0` GIDEON runs at one office (spec §21).

Then 52 lines with this release's, newest first, each in one fixed shape — the tag as an inline link to its file, an em dash, the ISO date, an em dash, a phrase under about 120 characters, the phrase the file's own opening clause or the README's status clause for the tag. `upgrade`'s reader is untouched: it keeps finding a tag's file by `git ls-tree` on `docs/2-changelog/` and the version suffix; the root file is a reader's index, not a product path.

`tests/test_changelog_index.py` holds it, in the tripwire shape (`Finding` rows with path, line, problem, and fix; every rule over an injectable root; the committed tree asserted clean): every release-shaped file has exactly one line; every line parses, its target exists, and its link text's version equals the filename's; the lines are newest first by version tuple; each date equals the date in the target's title line, derived and never restated; the phrase is non-empty; the preamble names `## Breaking` and `upgrade`. ### The contributor's templates

`.github/ISSUE_TEMPLATE/config.yml` turns blank issues off and carries one contact link to the repository's security policy page. `bug-report.yml` and `enhancement.yml` are issue forms (the `name:` and `description:` keys GitHub's community-profile check reads): each opens with the notice — a vulnerability goes through `SECURITY.md`, never here; issues are triaged by the CSAs into the development repository's private tracker; no site-file value, secret, chat, matter, or client text — and closes with three required checkboxes: every hostname, address, directory name, and mailbox replaced by a placeholder; not a vulnerability report; the CC0 dedication in the contributor's words, waiving all copyright and related rights worldwide. The bug form collects spec §2.1's version triple — the product tag, the corpus lockfile or `none`, the eval set version or `none` (the code review's one Major finding: the plan had the tag alone) — the hardware profile or the no-GPU declaration as a free input (never a dropdown of `models.lock`'s names), the command and its rows shell-rendered, what was expected, what happened. The enhancement form takes the request, the reason, and what the contributor would accept instead, and says an enhancement is judged against the build spec and may be recorded as out of scope. `.github/PULL_REQUEST_TEMPLATE.md` opens with the dedication and lists the three checks, no office value and no secret, the tests as contracts, every pin's designated proposal route (the pin watch for the locks it watches, the rebuild runbook for a built pin, a maintainer's pull request for `models.lock` until the pin watch supports model pins, Dependabot for the dev toolchain and the action majors) with the coupled copies completed on the proposal's branch, and a vulnerability never disclosed in the open; a merged pull request appears in the next tagged release, credited in its release note. ### Dependabot, narrow and export-ignored

`.github/dependabot.yml`: two `updates` entries at the root, `pip` and `github-actions`, weekly on Monday at 01:00 in the office zone so the pull requests exist before the Monday review; the `pip` entry ignores `setuptools` by name, since Dependabot's Python fetcher reads `pyproject.toml` beside `requirements-dev.txt` and would otherwise propose moving the `[build-system]` floor, packaging metadata outside the ticket's scope; the `github-actions` entry groups every action bump into one pull request. The comment records that the product installs nothing from PyPI (spec §1.5, §2.3; `tests/test_host_import_boundary.py`), that the product's pins move through reviewed pull requests of their own (the pin watch's for `host.lock`, `images.lock`, and the two skill records; a maintainer's for `models.lock` until the pin watch supports model pins) and no Dependabot ecosystem reads them — the built image's `Dockerfile` takes its base as an argument, so a `docker` entry would find no tag to move — and that two of the five pins have a copy `tests/test_toolchain_pins.py` holds equal, so their bumps are proposals a person completes on Dependabot's branch: Playwright's until `tools/turns/chromium.py`'s constant and the box's headless shell move, PyYAML's until `pin-watch.yml`'s one-package install moves with it; a `ruff`, `mypy`, or `pytest` bump is green on its own. A Dependabot pull request runs the hosted `checks` with a read-only token and no secrets, and the box jobs' push-only condition keeps it off the runner. The file is export-ignored by its own line in `.gitattributes` (the user's ruling at discovery): Dependabot is enabled by the file's presence, so an exported copy would open bump pull requests on the public `main` that the export overwrites at every tag and nobody merges there; ticket 56's excluded-prefix list takes the path by a dated line written at the claim, and ticket 61's fifth criterion is amended for this one file.
