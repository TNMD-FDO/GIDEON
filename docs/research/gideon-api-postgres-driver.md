# The API image's Postgres driver — psycopg 3.3.6, verified against psycopg-binary 3.3.6 and Open WebUI v0.11.3's psycopg 3.3.4

Scope: general-turn ticket 07 (`.scratch/general-turn/issues/07-guardrail-trip-written-by-the-service.md`) — `gideon/guardrail.py`'s `write_trip_row` moves from running inside Open WebUI v0.11.3's container (ADR-0039) into `gideon-api`'s own image (ADR-0045), and the writer's `psycopg` import becomes the image's own dependency. This note answers how the image should carry the driver and whether the writer behaves the same on it as on the frontend's copy. `psycopg`'s own repository was cloned at tag `3.3.6`, commit `git rev-parse 3.3.6` in that clone (the tag psycopg's own `docs/news.rst` calls "Current release"); Open WebUI was cloned at tag `v0.11.3`, commit `2a960a59fe1dbbd35282f0556b3666d81102e781` — the same commit the sibling notes (`gideon-api-http-stack.md`, `owui-engine-connection.md`) resolve to. All PyPI facts are from `https://pypi.org/pypi/<name>/json`, fetched live on 2026-09-20. `images.gideon`'s own build-argument pins for the driver do not exist yet (this ticket creates them); the note is bound to `images.gideon`'s base tag instead, per the task's own instruction.

**Recommendation, up front:** **(a) `psycopg` + `psycopg-binary` wheels**, both pinned to `3.3.6`, installed with the image's existing `pip install --no-deps --only-binary=:all: --no-cache-dir "psycopg==${PSYCOPG_VERSION}" "psycopg-binary==${PSYCOPG_BINARY_VERSION}"` shape, `PSYCOPG_VERSION` and `PSYCOPG_BINARY_VERSION` both watched as `pypi_project` pins (matching the ten packages `images.gideon` already pins this way) and kept at the same value by the ticket that bumps them (§2). §3 and §6 below are why: the binary wheel needs no apt package, no `RUN` step beyond the existing `pip install` block, and (per §6) its LGPL-3.0 terms ask nothing further of an image GIDEON builds on its own box and never distributes. Reject (b) `psycopg` wheel + apt `libpq5`: it adds the image's first `apt-get` step (crossing `built-images.md`'s apt egress-allowlist boundary this image doesn't cross today) for a wheel §1/§3 show is directly available, buys nothing in reliability GIDEON doesn't already have from (a), and its `ctypes.util.find_library`-based libpq discovery (§3) is real but is a second thing to keep working across every future `-slim` base bump that (a) simply doesn't have.

## 3. Binary wheel vs. system libpq

**What `psycopg-binary`'s wheel bundles.** Read from psycopg's own CI at the `3.3.6` tag, `.github/workflows/packages-bin.yml` and `.github/workflows/build-and-cache-libpq.yml`:

```yaml
env:
  LIBPQ_VERSION: "18.6"
  OPENSSL_VERSION: "3.5.8"
```

`packages-bin.yml`'s Linux job builds the wheel with `pypa/cibuildwheel`, `CIBW_BEFORE_ALL_LINUX: ./tools/ci/wheel_linux_before_all.sh` (which in turn runs `build_libpq.sh` — confirmed by the companion `build-and-cache-libpq.yml`'s identical `LIBPQ_VERSION`/`OPENSSL_VERSION` env and its comment that both workflows build and cache the same libpq artifact), and `CIBW_REPAIR_WHEEL_COMMAND: ./tools/ci/strip_wheel.sh {wheel} && auditwheel repair -w {dest_dir} {wheel}`. `tools/ci/build_libpq.sh` builds OpenSSL from source into a private prefix (`./config ... zlib -fPIC shared`) and then libpq from the tagged PostgreSQL source (`postgres_tag="REL_${postgres_version//./_}"`, i.e. `REL_18_6`) against that OpenSSL, with `--with-gssapi --with-openssl --with-pam --with-ldap`; `auditwheel repair` is what vendors every non-manylinux-baseline shared object the compiled extension links against into the wheel itself, which is why the docs describe the binary package as self-contained (below). **So the 3.3.6 binary wheel bundles libpq 18.6 built against OpenSSL 3.5.8**, plus whatever of the GSSAPI/LDAP/PAM support libraries `auditwheel` judged non-baseline. **Flag**: this is the CI *workflow's* declared build inputs at the `3.3.6` tag, not a direct inspection of the published wheel's `.libs`/`RECORD` contents (not extracted in this pass) — confirmed independently, though, by the empirical `psycopg.pq.__build_version__` read in §2 (`180006` = 18.6.0), which is the actual built-in libpq version the installed wheel reports at runtime, not just the CI declaration.

**psycopg's own installation docs, quoted, from `docs/basic/install.rst` at the `3.3.6` tag** (`https://www.psycopg.org/psycopg3/docs/basic/install.html`, matching this tag's rendered text):

> "Binary installation ... The quickest way to start developing with Psycopg 3 is to install the binary packages by running: `pip install "psycopg[binary]"` This will install a self-contained package with all the libraries needed." — under a table row marking `binary-installation` "(recommended for most users)".

> "Local installation ... The library will include the speed-up C module and will be linked to the system libraries (`libpq`, `libssl`...) so that system upgrade of libraries will upgrade the libraries used by Psycopg 3 too. **This is the preferred way to install Psycopg for a production site.**" (requires a C compiler, Python dev headers, `libpq-dev`, `pg_config` — none of which GIDEON's image installs today.)

> "Pure Python installation ... without `[c]` or `[binary]` extras you will obtain a pure Python implementation... **The pure Python installation is much slower than the binary-installation or local-installation. It is likely sufficient for local developments or small tasks but, for production loads, you might want to install one of the speed-up extensions too.** ... you will need the `libpq` PostgreSQL client library installed on your client (which will be imported dynamically via `ctypes`); for example on Debian systems you will probably need: `sudo apt install libpq5`."

Read together, psycopg's own docs put **`[c]` (local, compiled) first as "the preferred way ... for a production site"**, with binary second ("recommended for most users" — i.e., most convenient, not most preferred for production) and pure-Python last with an explicit slowness warning. `[c]` is unbuildable under GIDEON's `--only-binary=:all:` constraint (§1, no `psycopg-c` wheel exists), which leaves **binary** as the docs' actual top production-fit recommendation reachable here — the writer opens and closes one connection per trip, at most a few times a minute, so binary's per-call overhead relative to `[c]` (identical libpq, compiled Cython glue vs. slower ctypes calls for the pure-Python path) is immaterial at GIDEON's call volume; the docs' "production" language is about the pure-Python path's C-call overhead under real load, not about this writer's shape.

**The Debian trixie alternative.** `libpq.so.5` in trixie is supplied by **`libpq5`, version `17.11-0+deb13u1`** (Debian's package tracker, `https://sources.debian.org/api/src/postgresql-17/?suite=trixie`; `api.ftp-master.debian.org/madison?package=postgresql-17` confirms the same version across `source, amd64, arm64, ...`). Note this is **libpq 17.11, not 18.6** — a full major version behind the binary wheel's bundled libpq — libpq's own client/server protocol is backward-compatible across major versions so this does not break connectivity to GIDEON's Postgres 18 server, but it means the pure-Python route and the binary-wheel route are not running the same libpq.

**How pure-Python `psycopg` locates libpq**, read from `psycopg/psycopg/pq/misc.py` at the `3.3.6` tag: on any POSIX platform other than macOS, `find_libpq_full_path()` calls `ctypes.util.find_library("pq")` — stdlib `ctypes.util`, not psycopg's own code, from that point on. CPython 3.14's own `ctypes/util.py` (read directly from this sandbox's installed `/usr/lib/python3.14/ctypes/util.py`, matching upstream) implements Linux's `find_library` as:

```python
def find_library(name):
    return _findSoname_ldconfig(name) or \
           _get_soname(_findLib_gcc(name)) or _get_soname(_findLib_ld(name))
```

`_findSoname_ldconfig` runs `/sbin/ldconfig -p` and greps its cache; the two fallbacks need `gcc`/`cc` or `ld` (binutils), **neither of which the image installs** (the Dockerfile's own header comment: "nothing is compiled in the image"). So the pure-Python route's libpq discovery in a `-slim` image lives or dies on `/sbin/ldconfig -p`'s cache alone. This is answerable, not a coin flip: `/sbin/ldconfig` itself ships in **`libc-bin`**, which Debian's package page marks **`[essential]`** (`https://packages.debian.org/trixie/amd64/libc-bin`, `Package: libc-bin (2.41-12+deb13u4) [essential]`; its file list includes `sbin/ldconfig`) — an essential package is present on every Debian install including `-slim` variants (Debian's `-slim` Docker images strip apt/doc caches, not essential packages), so `ldconfig` itself is there. Installing `libpq5` via `apt-get install` runs dpkg's `ldconfig` trigger as part of that same `RUN` step, which populates the cache with `libpq.so.5`'s entry before the layer commits — this is standard dpkg/`libc-bin` trigger behavior, not something the Dockerfile would need to invoke explicitly (`images/postgres/Dockerfile`'s own `apt-get install -y --no-install-recommends "pgbackrest=${PGBACKREST_VERSION}"` is the existing GIDEON precedent for this apt shape). **Flag — could not verify inside the actual target image**: this sandbox has no Docker access (`docker pull` returned "permission denied while trying to connect to the docker API"), so the ldconfig-cache-after-`apt-get install` claim is reasoned from documented Debian trigger behavior and the essential-package fact, not observed inside a running `python:3.14-slim-trixie` container with `libpq5` installed. Recommend a one-line confirmation (`python3 -c "import ctypes.util; print(ctypes.util.find_library('pq'))"` after the apt step) if option (b) is ever chosen.

**One further wrinkle for a bare `psycopg` (no `[binary]`) install found via a live upstream issue, not documentation**: psycopg's own GitHub issue #1171 ("ImportError: no pq wrapper available when using psycopg or psycopg-binary in a distroless Docker container", closed, `dvarrazzo`/`adamsol`, `https://github.com/psycopg/psycopg/issues/1171`) shows a reporter who installed `psycopg-binary` **alone** (no `psycopg` wheel) getting `ModuleNotFoundError: No module named 'psycopg'` — `psycopg-binary` supplies the compiled backend only, not the `psycopg` top-level package; the fix was installing both, exactly what §1's recommendation already does. A separate commenter on the same issue reported needing `zlib` in a *distroless* image for `psycopg-binary` 3.2.12+ to import at all — zlib is part of the manylinux wheel-building policy's system-library allowlist, so `auditwheel` does **not** bundle it into the wheel, and the wheel expects it on the host. This is not a risk for GIDEON's image specifically: `pip install`'s own wheel extraction already exercises CPython's `zlib` stdlib module against the base image's libz today, for every wheel the existing Dockerfile installs (starlette, uvicorn, httpx, …) — if `zlib1g` were missing from `python:3.14-slim-trixie`, today's `pip install` step would already be failing, so this is confirmed present by the image's own existing behavior, not by a separate check. Flagged here because it is the kind of failure this ticket's silent-`except Exception` writer would swallow without a trace (§5's operational note).

**`psycopg.pq.__impl__` in each case**: `python` for the pure-Python/`ctypes` route (`psycopg/psycopg/pq/pq_ctypes.py:35`, `__impl__ = "python"`), `c` for the compiled `psycopg[c]` route (`psycopg_c/psycopg_c/pq.pyx:15`, `__impl__ = 'c'`), and `binary` for the `psycopg-binary` route — `psycopg-binary` is built from the same `psycopg_c` source tree, and `tools/ci/copy_to_binary.py`'s `sed_i(r"__impl__\s*=.*", '__impl__ = "binary"', target / "psycopg_binary/pq.pyx")` is the exact line that rewrites it at package-build time. §2's empirical check (`binary 180006 180006`) confirms this reports `binary` in practice, not just in source.

## 5. Sync `connect()` in a daemon thread under asyncio/uvicorn

**Thread safety**: `psycopg/psycopg/__init__.py:43` sets `threadsafety = 2` (DB-API 2.0's "Threads may share the module and connections" level), and `docs/advanced/async.rst` states plainly: "`Connection` objects *are thread-safe*: more than one thread at time can use the same connection." GIDEON's writer doesn't share connections across threads at all (`dispatch_trip_row` starts one fresh `Thread(daemon=True)` per trip, which opens and closes its own connection inside `write_trip_row`), so this is a non-issue either way — noted for completeness.

**How `connect_timeout` is enforced — Python-side wait loop, with one real gap.** Read from `psycopg/psycopg/connection.py`'s `Connection.connect()` at the `3.3.6` tag: `timeout = timeout_from_conninfo(params)` is computed once, then for each host attempt, `gen = cls._connect_gen(conninfo); rv = waiting.wait_conn(gen, interval=_WAIT_INTERVAL, timeout=timeout)`. `_connect_gen` starts a non-blocking libpq connection with `pq.PGconn.connect_start(...)` (`psycopg/psycopg/generators.py`) and yields whenever it would block; `waiting.wait_conn` (`psycopg/psycopg/waiting.py`) polls the connection's socket with a `selectors.DefaultSelector`, tracking `deadline = monotonic() + timeout` and raising `psycopg.errors._WaitTimeout` — caught in `connect()` and re-raised as `psycopg.errors.ConnectionTimeout` — once `monotonic() >= deadline`. **This is a genuine Python-level deadline over a non-blocking libpq handshake, not a single blocking C call**: the socket connect, TLS negotiation, and startup-packet exchange are all covered by this one `deadline`.

`timeout_from_conninfo` (`psycopg/psycopg/conninfo.py`) documents its own rounding rule in a comment ("Follow the libpq convention... 0 or less means no timeout... at least 2 seconds"): `timeout = int(float(value))`; `if timeout <= 0: timeout = _DEFAULT_CONNECT_TIMEOUT` (130 s); `elif timeout < 2: timeout = 2` (a hard 2-second floor). **GIDEON's `TRIP_CONNECT_TIMEOUT_SECONDS = 3` (an int) passes through unchanged** — above the 2 s floor, so the writer gets exactly the 3-second bound it asks for.

**The real gap: DNS resolution of the host is *not* covered by `connect_timeout` at all.** `Connection.connect()` calls `attempts = conninfo_attempts(params)` **before** entering the `for attempt in attempts:` loop that `wait_conn`'s deadline wraps — i.e., host resolution happens outside the timed section entirely. Read directly from `psycopg/psycopg/_conninfo_attempts.py` (`3.3.6` tag, and confirmed identical at `3.3.4` by the same-tag diff in §4): `conninfo_attempts()` calls `_resolve_hostnames(attempt)` for each host, which — when the host isn't already an IP or a Unix-socket path — calls plain **`socket.getaddrinfo(host, port, proto=socket.IPPROTO_TCP, type=socket.SOCK_STREAM)`**, a blocking stdlib call with **no timeout argument and no deadline wrapped around it anywhere in this code path**. The module's own docstring names the reason: "Because the libpq async function doesn't honour the timeout, we need to reimplement the repeated attempts" — psycopg replaced libpq's own (also DNS-resolving) connection start with this Python-level `getaddrinfo` specifically to support the multi-host retry list, but did not give that call a timeout of its own. (The `docs/api/dns.rst` note that `AsyncConnection.connect()` performs "non-blocking name resolution automatically" refers to this same `_resolve_hostnames`-family function's `asyncio.get_running_loop().getaddrinfo(...)` await in the async path — non-blocking *to the event loop*, but still no explicit deadline of its own either; the sync path's plain `socket.getaddrinfo` is the one GIDEON's writer actually takes.) **This is the one place `connect_timeout=3` does not bound the writer's daemon thread**: if resolving `host="postgres"` hangs — a slow or non-responding resolver, not merely a refused or absent TCP listener — the thread blocks in `getaddrinfo` for however long the underlying resolver takes, unbounded by anything psycopg or GIDEON's own code sets. In practice `host="postgres"` resolves through Docker Compose's embedded DNS server on the project's internal network, which is normally fast (or fails fast with NXDOMAIN if the service name is genuinely absent from that network) — but this is an operational property of Compose's DNS, not a guarantee `connect_timeout` or any documented psycopg behavior provides. **Flag for the ticket's invariant**: the "refused or unreachable database never fails or delays the turn" criterion holds cleanly for a **refused** connection (TCP `ECONNREFUSED` — immediate, well inside `wait_conn`'s 3 s deadline) and for an **unreachable-but-resolved** host (times out at exactly `connect_timeout`, 3 s, via `wait_conn`'s deadline) — the ticket's own two named cases. It is *not* proven bounded for a **stuck DNS resolution** of the host itself, which this note could not find any psycopg-side timeout for; the daemon thread's life in that specific case is bounded only by the daemon flag itself at interpreter shutdown (below), not by `connect_timeout`. Recommend this be an explicit case in the ticket's own unit-test checklist item ("a refused or unreachable database leaves the turn's answer and its timing untouched") if it isn't already, or confirmed as out of scope because `host="postgres"` is a Compose service name whose resolution failure mode is already known to be fast.

**Context manager commit-and-close**: confirmed unchanged at `3.3.6`, `psycopg/psycopg/connection.py`'s `Connection.__exit__`: on clean exit, `self.commit()` then `self.close()` (if not pool-owned); on an exception, `self.rollback()` (swallowing a rollback failure with a `logger.warning`, never re-raising it over the original exception) then `self.close()`. `Connection.connect(..., autocommit: bool = False, ...)`'s default, and `BaseConnection.__init__`'s `self._autocommit = False`, are both unchanged — matching what the writer's two `connection.execute(...)` calls inside the `with connect(...) as connection:` block rely on: nothing commits until the block exits cleanly.

**`Connection.execute` with `%s` parameters**: `Connection.execute(query, params=None, *, prepare=None, binary=False)` (`connection.py`) delegates to `self.cursor().execute(query, params, prepare=prepare)` — the writer's `connection.execute("INSERT ... VALUES (%s, %s, %s, %s)", (row.branch, row.family, row.pattern_id, row.source))` shape is exactly this signature, unchanged between 3.3.4 and 3.3.6 (§4).

**Daemon threads holding an open connection at interpreter shutdown**: psycopg's own docs say nothing about this (searched `docs/*.rst` and `psycopg/psycopg/*.py` for "daemon"/"atexit" — only hits are `_acompat.py`'s unrelated `daemonize_thread` helper and `docs/advanced/pool.rst`'s `atexit.register(pool.close)` recipe for connection *pools*, not single ad hoc connections). This is a plain Python `threading` fact, not a psycopg one: CPython 3.14's own `threading` docs (`https://docs.python.org/3.14/library/threading.html`) state it directly — **"Daemon threads are abruptly stopped at shutdown. Their resources (such as open files, **database transactions**, etc.) may not be released properly."** — naming exactly this scenario. GIDEON's writer already matches the doc's own remedy in spirit for the *common* case (the connection is a `with`-block that closes itself on every normal return path, well before the thread's target function returns), so this only bites if the interpreter exits while a `write_trip_row` thread is genuinely still inside a stuck `connect()`/`execute()` call — the DNS-hang case above being the one scenario this note found where that's possible without a bound.

**Upper bound on the daemon thread's life, stated plainly**:
- **Refused connection** (`ECONNREFUSED`, e.g. Postgres container down but the network reachable): bounded by the OS's near-immediate `ECONNREFUSED`, well under `connect_timeout`'s 3 s.
- **Unreachable host** (connectable network, no response — e.g. a firewalled or silently-dropping host): bounded by `connect_timeout` = 3 s exactly, enforced by `wait_conn`'s Python-side deadline (above).
- **Slow/failed statement** (host reachable, query slow): bounded by `statement_timeout=3000` (3 s), a server-side GUC set via the `options` startup parameter — enforced by Postgres itself, not by psycopg client-side code (`options` is passed through to libpq's conninfo unchanged; nothing psycopg-specific to verify here beyond that libpq honors arbitrary `-c` GUC settings in `options`, which is documented PostgreSQL behavior, not psycopg's).
- **Stuck DNS resolution of the host**: **unbounded by any psycopg or GIDEON-set timeout** found in this pass (above) — bounded in practice only by whatever the OS resolver itself gives up after (glibc's own resolver timeout defaults, not investigated here as out of psycopg's scope) and, failing that, only by the daemon thread being killed at interpreter shutdown.
