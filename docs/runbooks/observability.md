# Observability and alerting

This runbook arrived with `v0.0.22`. Prometheus, Grafana, and exporters watch the box. Their configuration is rendered and applied with the services, so a release can restore the whole monitoring setup; apply is the command that brings the running stack in line with the site file and verifies it.

**Grafana is the one alert engine**: its release files define the page-class rules, email contact point, and notification policy, and Grafana sends alerts through the office relay in `alerts.smtp` to `alerts.recipients[]`. There is no Alertmanager, because keeping one alert engine leaves one place to follow a page. The three kinds of record serve different purposes: kept facts are `audit_log` rows that can be queried, container logs are in journald (90 days, 50 GB), and metrics are Prometheus series (one year).

## 1. What runs, and where it lives

Neither `/data/observability/` directory is in the backup set, because the boards and rules come back from the release at the next `apply` and every fact that must survive is already an `audit_log` row the set carries. A lost Grafana is recovered by `apply` plus a directory login. A rollback to a release before `v0.1.17` leaves the "Engine down" rule provisioned, because Grafana's file provisioning deletes nothing without an explicit `deleteRules` entry, which an older tree cannot carry. The rule then reads no data and stays Normal, inert until the directory is recreated.

## 2. Getting in

- **Admins-group members** sign in at `/grafana/` with their directory account name and password. Grafana maps the admins group, and only it, to organisation Admin with server-admin rights. A directory user outside the group is refused at the login form, with Grafana's log saying the user belongs to no mapped group; no Grafana record is written, so there is nothing to clean up.
- **The break-glass administrator** is the local account `grafana-admin`. Its password was generated by the first `apply` after `v0.0.22` and printed once, and it is in the office password manager and in `/etc/gideon/secrets/grafana_admin_password`, which is root-readable. Use it when the directory is what is broken. The frontend has its own break-glass administrator, and the two are different accounts.

  To rotate the password, or when the stored one is one nobody knows, run `gideon secrets rotate grafana_admin_password`, which resets Grafana's stored value through its own CLI and rewrites the file. Copy the new value into the office password manager.
- A sign-in lands on the **Overview**, Grafana's home, whose first row shows the pages firing now and links to the other boards and the start-here card (§3).
- Provisioned boards, rules, contact points, and the policy are **read-only in Grafana**. A change to them is made by a release and not by a click in Grafana, though silences are allowed (§5).

## 3. The boards (folder GIDEON)

Every board's header lists the other GIDEON boards, the Overview among them. Every card's (i) beside its title says what it shows, what a bad value means, and the runbook section to follow.

- **Overview.** First, *Needs attention* lists the page-class alerts firing now, read from the same alert state `gideon status` prints, so an empty list means a clear box. Beside it, *Start here* has `gideon status`, Grafana's silences page, a link to each other board on this host, and the start-here card on the box and in the public export.

  Below them is one card for each measure a page rule grades, with each coloured card turning red at the line its page fires at. *Services and probes* has one tile per metrics scrape, door probe, and database check a down-rule watches, reading up or down; each tile is named under "The tiles on *Services and probes*" below. Its card spans the row so each name shows whole, with a long one on two lines.

  Three bars show `/data`, `/`, and `/var/lib/docker` free, turning red under the 15 % line. The certificate card shows its days left and turns red under the 14-day line. Backup set age and push age come from the rows and turn red past the 26-hour line. The newest passing drill's age turns red past the drill-overdue line set by the drill calendar, and the last drill's result is shown. Then *Guardrail trips* shows the users' daily trips.

  At the foot, the collapsed *Host detail* row holds host load, host memory, each GIDEON container's memory in use, and each one's share of its limit; no rule pages on them. `/data/fast` is not paged and not shown. A tile turns red at once while its rule waits out its pending period, so a red tile is a page on its way.

- **Backup.** The board shows the last 35 days of M25 (run duration, set bytes, hard-link ratio, push transferred share, push duration, verified and pruned counts) and M26 (drill duration and result) as series over the rows.

  The drill table shows the five newest results, and the last ten runs table shows each row's result and the share of sampled files reused. A run, push, prune, or restore reads `completed` when it has no recorded result, while a drill shows its own result word.

  The pruned counts read the prune's own `backup_prune` row.

- **GPU.** The board shows per-GPU utilization, each card's used and free memory in GiB with its current figures in the legend, temperature, power, and the driver version from DCGM. The temperature card's dashed line is each card's own maximum operating temperature, read through the exporter; a card that reports no limit draws no line. At or above the line, the card slows itself, so check the room's cooling and airflow. Temperature does not page.

  From the engine's own `/metrics`, the board shows KV-cache usage, requests waiting and running, and *Answer speed*: tokens per second while a request is being answered, measured across the board's time range. Answer speed is empty when no request ran in that range, and a figure well below the usual one means answers arrive slowly for everyone. It is uncoloured because no page rule sets a line; answer speed does not page.

- **Eval.** On GPU hosts only, the board shows the newest run of each suite and kind and each nightly verdict as a point, with an aborted run distinct from a failed run.

  The guardrails gate's counts per family sit beside the run verdict and the replaced-control ceiling, with blocked positives split as model declined, code replaced, and answered without its figure. The harness's and judge's false-refusal counts and unread controls are also shown.

  Run duration is shown against the nine-hour night, along with the failed case IDs of the newest nightly runs. The Proposals waiting table shows the newest daily tally, its completeness, and its recorded trigger rows.

  Below it, *Last eval trip* shows the age of the eval identity's last deliberate guardrail trip, which every `engine verify` refreshes. The eval identity is the account GIDEON's own test turns sign in as.

  M17 and M18 have no panel yet; their measurements arrive with the user and synthesis work.

- **Corpus.** On every host, the board has tables of the newest build report of each generation not retired: documents per court by status, source text column, and precedential status; failures by reason; anchored documents, agreement counts, and the accounted gate; and the build's wall clock. Failures or a failed gate need investigation.

  The lifecycle span is creation to built, including gaps between commands, rather than a build duration. Below, the bulk embed shows recorded generation progress, then the embedding server's requests waiting and the mean in inference, tokens embedded and requests answered per second, and request latency. The in-inference figure is a mean over the chart's window, not a count. A growing queue with no progress can mean a stalled build. Server cards are empty without a GPU, and rates and latency are empty while nothing embeds in the range.

  The stores show lexical heap against its limit, vector memory, each collection's points and vectors, work in flight, and documents indexed per second per index, with a band beside it reading whether lexical indexing is throttled. Each chart names a generation by its lockfile and shows its current value in the legend. A heap near its limit or a band that stays "throttled" can slow indexing.

  The worker shows jobs waiting and jobs running per queue as two charts, with one hue per queue across both, then heartbeat age and job slots. A stale heartbeat can mean the worker stopped. Nothing on this board pages.

  M20, M21, and M23 have no panel yet: the first two await the research turn, the third the US Code.

The node exporter runs on the private network with the host's root mounted, so its network-device series describe the container's interfaces, not the host's; disk, memory, load, filesystems, and systemd units are the host's.

### The tiles on *Services and probes*

Each tile is one check, and its name is the short name Prometheus knows the check by. There are three kinds:

- **A plain name** (`node`, `caddy`) is a metrics read: Prometheus asked that service for its figures and got an answer, so the service is running.
- **A name ending in *probe*** (`ingress probe`) is a door check: the blackbox exporter, a small service whose only job is to make test requests, sent a real request and got a healthy answer.
- **A name ending in *database*** (`postgres database`) is the database check: the Postgres exporter signed in to the database.

The checks the blackbox exporter makes show two tiles each: `ingress`, `frontend`, and `opensearch`, and where they exist `search` and `api`. For those, the plain tile says only that the blackbox exporter ran the test, and the *probe* tile says the service passed it. Read the *probe* tile for the service's health. If the plain tile is down, the tester is what failed, the *probe* tile has no reading, and the page is `Target down`; the table's last column names the *probe* tile's page.

| Tile | What it checks | Its page (§4) |
|---|---|---|
| `prometheus` | Prometheus, the store that keeps every figure the boards and the page rules read. | `Target down` |
| `grafana` | Grafana's own figures. A stopped Grafana shows no board and sends no page; the missing Saturday email (channel heartbeat) is its alarm. | `Target down` |
| `node` | The node exporter, which reports the host itself: disks, memory, load, and systemd units. While it is down the free-space bars and the backup-unit rule have nothing to read. | `Target down` |
| `cadvisor` | cAdvisor, which reports each container's memory and processor use: the *Host detail* row's container memory. | `Target down` |
| `dcgm` | NVIDIA's DCGM exporter, which reports the graphics cards: everything on the GPU board's first two rows. A GPU host only. | `Target down` |
| `engine` | The engine, the model server that writes every answer. A GPU host only. | `Engine down` |
| `embed` | The embedding server, which turns text into the vectors search runs on. A GPU host only. | `Target down` |
| `caddy` | Caddy, the web server every browser reaches first; this tile says it is running, not that the way in works. | `Target down` |
| `ingress`, `ingress probe` | The way in. The test asks Caddy for the site over HTTPS under the box's own hostname, as a browser does, and passes only when the site answers with a certificate the office CA signed. The same test reads the certificate's days left. Caddy can be running while this fails, on an expired certificate for one. | `Ingress probe failing` |
| `frontend`, `frontend probe` | The chat frontend, the page users type into. The test asks the frontend directly, on the box's private network, whether it is healthy. | `Frontend probe failing` |
| `search`, `search probe` | SearXNG, the web search General uses. The test asks it directly whether it is healthy. Present only while `web.search` is on; with it down General still answers, without search. | `Search probe failing` |
| `api`, `api probe` | `gideon-api`, GIDEON's own service between the chat frontend and the engine: every General turn passes through it. The test asks it directly whether it is healthy. A GPU host only. | `API probe failing` |
| `worker` | GIDEON's job worker, which runs the queue's jobs. The tile is up when Prometheus can read its figures and the worker can count its queue. | `Target down` |
| `postgres` | The Postgres exporter, which reports the database's figures. | `Target down` |
| `postgres database` | The database itself: the exporter signed in to it. | `Postgres down` |
| `qdrant` | The vector index, read from its numbers page; this tile says the store is running. | `Target down` |
| `opensearch`, `opensearch probe` | The full-text index General's search will read; nothing reads it yet. The test asks for its own health answer, which needs no password. | `OpenSearch probe failing` |
| `opensearch-metrics` | The store's own figures through its metrics plugin, under a password that reads figures and nothing else. | `Target down` |

Only the `ingress` test goes through the web front door; the `frontend`, `search`, `api`, and `opensearch` tests reach their service directly. So `ingress probe` down with those probes up means the services work and the way to them does not.

## 4. What pages, and what to do

Every page-class email lists each alert on two lines. The first carries its status, its rule, and its summary, and the second carries only the runbook's link in the public export at the running release, with its section beside it; the link resolves once that release's export has run. Grafana's default body, with its labels, values, and buttons, is gone, and a silence is made in Grafana itself (§5). The email ends with one line: run `gideon status` on the box, then follow the runbook named above.

The rule set is a release file, `compose/grafana/provisioning/alerting/rules.yaml.tmpl`. A condition that stays unresolved is re-sent daily, and acknowledgement follows business hours. The upstream watch notice is the exception: it is emailed once and never re-sent or resolved by mail. Saturday's heartbeat is not a page and takes none of this format, since its own contact point sends `[GIDEON <office>] Channel heartbeat` with the two fixed body lines in the table below.

`gideon status` lists the pages firing now, each with its rule's runbook path on the box and its section. It exits 0 when nothing needs attention, 1 when a page is firing or `sudo` itself refused, and 2 when status could not check or the installed command itself refused, for example because the install home has no checkout.

The Rule column spells each title exactly as a page email's subject, `gideon status`, and the Overview's *Needs attention* list spell it, so the row to follow is the one under that name.

## 5. Silencing during planned work

Before a planned outage (a restore, a NAS maintenance window, a driver move), create a **silence** on Grafana's silences page (Alerting → Silences), linked from the Overview's *Start here* panel. Match `alertname` to the rule's title as §4's Rule column spells it and set an end time. Silences are Grafana state rather than release content and expire on their own.

A silence stops the email alone: the rule stays listed on the Overview's *Needs attention* panel until its condition clears, while `gideon status` marks it `silenced` and does not count it. Grafana keeps sending a cleared rule's resolved alert for 15 minutes, so a silence that ends sooner after the condition clears still lets the resolved email through. Set the end at least 20 minutes past the planned work.

Do not silence the heartbeat. Before an engine restart expected to take longer than five minutes, such as a model or image bump's cold recreate on a box whose compile cache is gone or a first install, silence `Engine down`. A plain stop/start and an ordinary apply's recreate stay under the rule's period and need none.

Before a decision weekend's run starts, silence `Nightly run overdue` for the planned skip and let the silence expire after the next nightly run.

## 6. Retention and where things are kept

- Prometheus keeps one year, set by `--storage.tsdb.retention.time=1y` and visible at `http://127.0.0.1:9090/api/v1/status/runtimeinfo` on the box.
- journald keeps container logs for 90 days or 50 GB, as configured in `/etc/systemd/journald.conf.d/gideon.conf`. Read the usage with `journalctl --disk-usage`; `journalctl CONTAINER_NAME=gideon-grafana-1` reads one service across recreations.
- Rows live a year in `audit_log`'s monthly partitions.
- Chats idle past the site's `retention.chats` (default 90 days from last activity, archived and pinned chats included), the uploads they name, and the feedback rows past the same interval or left on a swept chat are deleted nightly at 02:00. Read the run's counts with `journalctl -u gideon-retention-sweep.service`; its `retention_sweep` and `chat_swept` rows are in `audit_log`.
- No search-query text reaches a log since `v0.1.35`.

  SearXNG's journal carries no request line. Since that tag, the rendered `searxng/logging.json` holds its network logger at ERROR, so the journal carries no `HTTP Request failed` warning naming an engine's URL. The engines' `ErrorContext` lines still name each failure by hostname.

  The frontend's audit file is `/data/bulk/openwebui/audit.log`, with its rotated archives beside it. A `Web search failed` traceback in the frontend's journal, printed only when SearXNG itself answers an error, is the one line a query can reach.

  When a fetch fails, the frontend's page loader prints a fetched page's address in a retry warning, a blocked-URL warning, or a content-loading traceback. The line carries a third party's URL and not the query, the second recorded residual (`v0.1.38`). Every log source was enumerated by hand for that release.

## 7. Inducing each page (the acceptance pass, and after a relay change)

Each induced condition should arrive by email within the rule's `for` window plus the policy's group wait; clear it afterwards and confirm the resolved notice.

1. **Target down**: Run `docker compose -f /etc/gideon/rendered/compose.yaml stop node-exporter` and wait ten minutes. ## 8. Secrets and the service group

Every secret file under `/etc/gideon/secrets/` is `root:gideon` 0440, except the backup keypair, which keeps its own ownership. Grafana, the Postgres exporter, and `gideon-api` run unprivileged and read their secrets through that group, using `group_add` in the rendered Compose file; `gideon-api` reads both the engine and API key files. A secret a CSA places by hand as `root:root` converges at the next `gideon host provision` in its `secrets-dirs` step, since provision brings the box's host layer to its target state.

## 9. Egress

The DCGM exporter image comes from `nvcr.io` (the only registry that publishes it); the office firewall must allow it for `registry mirror` and the CI runner (`config/egress.yaml`, `office-services-setup.md`). cAdvisor comes from GHCR, already allowed.

Grafana fetches nothing from the internet by itself, at a start or on a timer. The release turns off its update checks, usage report, plugin install, and signature-key refresh; Grafana runs only what the pinned image holds, and `config/egress.yaml` lists no host for it. Grafana reaches Prometheus and Postgres on the Compose network, and the office's mail relay and directory.

A signed-in person's actions cannot fetch profile images from Gravatar (every account shows the default image), publish a snapshot to Grafana Labs' public snapshot host (snapshots kept on the box still work), install plugins from the catalog, or load the news feed. Visiting the Plugins page still asks the box to fetch the catalog listing from grafana.com; no setting turns off that proxy. `config/egress.yaml` lists no host for Grafana. An office firewall that enforces the allowlist refuses the request, and each visit then logs one `level=error` "Proxy request failed" line; this is not a fault. Where the firewall does not enforce the allowlist, the listing loads. Either way, the page installs nothing.

## 10. The weekly nudge

The weekly email, subject `[GIDEON <office>] Proposals waiting`, says `Proposals waiting on this box: <count>` and then `Read them with gideon proposals.`, and nothing else: no proposal, trigger, or figure. It is a nudge, not a page, and `gideon status` does not list it. It comes on Monday between 08:00 and 09:00 office time while the count is above zero, and no email says the count went back to zero. The count comes from the latest daily tally. The Eval board's Proposals waiting panel shows the tally's instant, so check its age before acting on a count. Run `gideon proposals` to read the current proposals. If the tally stops, read `journalctl -u gideon-proposals-tally.service`. An open upstream notice is a `fired` row of the `upstream` section, so it counts in the nudge until a lockfile pins its date.

After a rollback to a release before this nudge, the provisioned rule keeps evaluating. Without its route, a firing rule pages through the root policy daily. Silence Proposals waiting in Grafana as described in §5 until the rule is restored or removed.
