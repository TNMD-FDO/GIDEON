# `gideon eval` runs from the host checkout on the standard library; §18.1's `httpx` and `numpy` are an allowance not taken

§18.1 describes the eval harness as "plain Python: stdlib + httpx + numpy", and `docs/ARCHI.md` §3 and §12 read as if `gideon eval` would therefore run from an image with those two dependencies installed. Slice-2 ticket 04, the first cycle to give the command a body, found that reading buys nothing it needs: the command is invoked as `sudo python3 -m gideon eval run` from the release checkout on the box's system Python, the hosted checks run the same module with no database, the frontend clients GIDEON already ships are `urllib` (ADR-0045's service is the exception that proves it, and it is not this command), the turn harness slice-2 ticket 11 moves under this command already runs on the host, and ADR-0023's formulas are arithmetic that `math` serves. The decision, the maintainer's ruling at the claim's discovery (2026-09-19), is that **`gideon eval` is a host command like every other: `gideon/evaluation/` imports the standard library, `yaml`, and `gideon` alone** — the same boundary `gideon/host/` holds (§9), enforced by an AST tripwire in `tests/test_evaluation_run.py` as `gideon/extraction/`'s is — and that §18.1's `httpx` and `numpy` are **an allowance this design does not take**, not a requirement it must meet. The allowance is not withdrawn: a later ticket that proves the standard library insufficient for a suite re-opens it as a supersession with its evidence, never by adding an import.

**Rejected:** running `eval` from an image with the two dependencies — it would put a second Python environment on the box for one command, give the eval harness a build and a pin to watch, and make an eval run depend on the registry and a pulled digest, none of which the `extraction` slice or any suite yet specified needs; taking the allowance pre-emptively "because the spec permits it" — an import taken is an import every later cycle builds against and no cycle removes, and the cost of proving the standard library sufficient is highest at the first cycle and falls thereafter; forbidding the allowance outright by amending §18.1 — the suites that read a ranked list or score a judge's agreement (slice-2 tickets 06, 08, 09) may yet want `numpy`, and a decision taken before their evidence exists would be taken on argument rather than measurement (ADR-0017's posture); putting the command under `gideon/host/` — it is not a bare-host command, it talks to the stack through `stack.exec_argv` like any other, and `gideon/host/` is the subtree provisioning must run before Docker exists.

**Consequences:** `pyproject.toml` lists `gideon.evaluation` beside `gideon.host` and `gideon.extraction`, and the package ships in every release with no new dependency; the `record` stage reaches Postgres the way `audit.py` does, one `psql` transaction through `docker compose exec` with every value bound as a variable, so the database driver question does not arise; §18.1's sentence and `docs/ARCHI.md` §3 and §12's phrasing are superseded by the dated spec-bug comment on greenfield [21] (slice-1 ticket 29's pattern — the spec is not edited), the map's §12 row carrying the as-built reading; the tripwire is the enforcement, so a cycle that needs a third-party import fails a test rather than shipping one, and the failing test is the prompt to write the supersession; `yaml` is in the allowed set only because the site file's loader is `gideon/host/site.py`'s, already inside the bare-host boundary that permits it, and no module of `gideon/evaluation/` parses YAML itself.
