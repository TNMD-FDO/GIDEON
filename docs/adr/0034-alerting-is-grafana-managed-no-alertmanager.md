# Alerting is Grafana-managed: the rules, the contact point, and the notification policy are provisioned release files; there is no Alertmanager container

ADR-0027 fixed the observability tier as Prometheus, Alertmanager, Grafana, and exporters, with "alerts are Alertmanager rules delivered by email". When slice-0 ticket 07 planned that tier, the page-class conditions split into two kinds: host, GPU, container, and probe conditions that are Prometheus series, and backup, push, and drill conditions that are `audit_log` rows — kept events, which ADR-0027 itself says Grafana reads through a read-only role. Alertmanager can evaluate only the first kind; the second would have needed a bridge (an exporter running release-shipped SQL, or the backup commands re-emitting their facts as text files) or a second alert engine. Grafana's unified alerting evaluates both kinds against its two datasources, and its rules, contact points, notification policies, and mute timings are file-provisioned — text in the release, rendered and byte-stable like the Caddyfile — and it delivers email itself through the office relay from `alerts.smtp.*`. So Grafana is the one alert engine and there is no Alertmanager container; `gideon alerts test` asks Grafana to test the provisioned contact point, and a weekly heartbeat rule exercises the whole path (rule → policy → contact point → relay) on a schedule. This supersedes ADR-0027's alerting sentence only; its stack, its "kept events are rows", and its rejections stand. Slice-0 ticket 07, `F_0.0.22`, Sept 2026.

**Rejected:** Alertmanager kept as Grafana's delivery target (a container whose only job is relaying what Grafana already decided, with a second SMTP configuration); a split by datasource — Prometheus rules through Alertmanager, row rules through Grafana (two rule engines, two SMTP configurations, two things `alerts test` must prove, two places to look when asking why something did or did not page); Alertmanager kept for the three things it has that Grafana lacks — a route for injecting a synthetic alert, a CA-file setting for the relay's certificate, and a `require_tls` that fails closed — each answered instead by the receiver test plus the heartbeat, by mounting the office CA into the Grafana container's trust directory, and by a mandatory-STARTTLS policy keyed to whether the site file names an SMTP user, the rule preflight's SMTP check already applies; Grafana-managed alerting with the built-in Alertmanager disabled in favour of an external one (the same two containers, one of them idle).

**Consequences:** the alert rule set is a release file under test — the rendered policy, the contact point built from `alerts.recipients[]`, and each rule's datasource reference are asserted by the render tests, and a rule over the rows is SQL a CSA can run by hand; `alerts test` proves the contact point and the relay, not the routing tree, which is a file under test and a Saturday-morning email; a dead Grafana pages nothing, since Grafana OSS has no watcher for its own silence — the heartbeat's absence is what a person notices, and the runbook says so; a Prometheus outage is itself a page, because the core-service rule alerts on no data and on execution error; provisioned rules are read-only in Grafana's UI, so a threshold change is a release, never a click (ADR-0028); the spec's §19.5, §20.1, and ticket 07's first criterion, which name Alertmanager, read "Prometheus is unreachable off-box; Grafana only through the ingress path", recorded as a spec bug on the ticket; slice 4's `gideon-api` gauges join the boards without moving the rules.
