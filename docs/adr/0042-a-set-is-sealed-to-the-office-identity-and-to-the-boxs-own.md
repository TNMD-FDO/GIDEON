# A set is sealed to the office identity and to the box's own; the office identity is the only key that opens a set off the box that made it

A backup set's one encrypted thing is its secrets tarball, and until now it was sealed to one age recipient whose identity lives only in the office password manager, so nothing on the box could open a set and the tag-triggered clean-VM full restore (slice-0 ticket 20) would need a person to hand it that identity — the one key the rule kept off the box so that whoever holds the push target, or a pushed snapshot, never holds the secrets. Root on the box already reads those secrets in plaintext under `/etc/gideon/secrets`, so a second identity that lives on the box alone exposes nothing root could not already read, and leaves the off-box copy exactly as sealed as before. The decision: **every set's tarball is sealed to two recipients — the office's, whose identity stays only in the password manager, and the box's own, whose identity is root-only host state at `/etc/gideon/backup_age_identity`, minted once by the `age-identity` provision step, never printed, and excluded from every set as the no-GPU marker is.** `backup run` derives the box recipient from the identity at run time and records both recipients in the manifest, the office's first; the drill expects as many recipient stanzas as the manifest names; a set from before this rule names one and still restores and drills. The box opens its own sets unattended; the office identity is the only key that opens a set anywhere else, a rebuilt box included. This supersedes spec §1.7's sentence "the age identity lives in the office password manager, deliberately not on the box" for the box's own identity only — the office identity still is not on the box — along with slice-0 ticket 06's criterion clause and greenfield ticket 22's item 9 (iii) parenthetical, each recorded as a comment. Slice-0 ticket 23, Sept 2026.

**Rejected:** a supervised identity step inside the tag-triggered run (a person in a loop the run exists to remove); copying the live plaintext secrets into the VM (the restore would then prove nothing about the tarball); the box's identity as a registry secret inside `/etc/gideon/secrets` (it would ride inside the very tarball it opens, and a restore would carry it onto another box); a public-half file for the box (a restore would carry a stale recipient onto a rebuilt box, and the half is derivable at run time); a site key or a command flag (host state is neither, ADR-0028 and ADR-0035); rotation of either identity (not a need this rule creates).

**Consequences:** the runbook's custody line — after a provision, after a total-loss recovery, and whenever the password-manager entry changes, a CSA derives the public half of the password manager's identity on their own machine and compares it with `/etc/gideon/backup_age_recipient`; a rebuilt box mints its own identity and opens earlier sets with the office identity alone; a restore in place never touches the live identity, since the restore applies the set's exclusions; `upgrade --rollback` to a tree that seals to one recipient removes the identity, since that tree's snapshots would carry it; the manifest stays version 1 with an additive `recipients` key and keeps writing the singular `recipient` for a previous tree (ADR-0005); slice-1 ticket 24's secret-rotation class does not see the identity, which is not a registry secret.
