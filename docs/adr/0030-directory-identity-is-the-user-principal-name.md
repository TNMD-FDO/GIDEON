# The frontend keys every human account by the directory's userPrincipalName, not the mail attribute

Open WebUI requires an email-shaped address to create an account and refuses an LDAP sign-in whose configured mail attribute is empty; the greenfield spec (§4.1, ticket 09 item 3) took that address from AD's `mail`. The first live sign-in showed the cost: `mail` is data entry, offices with a local directory often leave it blank (TNMD's admin accounts had none), and an account without it cannot sign in at all even though sign-in itself is by `sAMAccountName`. Every directory account has a `userPrincipalName` (`user@domain`), unique, email-shaped, and free, and nothing in GIDEON ever sends mail — the address is only the identity the frontend, the reconcile, and the audit log key a person by. **The frontend's mail attribute is therefore `userPrincipalName` for every office**, the reconcile joins directory members to frontend users on it, preflight refuses a users-group member without one, and the sign-in name stays `sAMAccountName`. This is a release decision, not a site key: no office fact distinguishes it, and a per-office attribute would make the same person a different account on two installs. Supersedes §4.1's "email from AD `mail`" and [09] item 3. Slice-0 ticket 05 (the finding) and ticket 09 (the change), Sep 2026.

**Rejected:** keeping `mail` and documenting the data-entry requirement (the runbook line shipped with v0.0.11) — it makes the office's least-maintained attribute a login prerequisite and fails at the worst moment, the first sign-in; a site key naming the attribute — an office fact only in the sense that some offices have skipped a chore, and it invites the two-installs-two-identities drift; synthesizing an address in the frontend — the frontend cannot, and a GIDEON-side shim would be the one thing standing between an office and its sign-ins.

**Consequences:** the switch must land before humans accumulate, because the frontend keys accounts by this address and an existing account keyed by `mail` is re-created under its UPN at the next sign-in (its chats and knowledge bases stay with the old row until reassigned); `mail` stays readable for offices that want real addresses later, but nothing depends on it; the audit log's user ids are unaffected (they are the frontend's ids); receiving-office runbooks lose the "set E-mail on every account" step.
