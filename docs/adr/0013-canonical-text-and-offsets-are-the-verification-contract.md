# Canonical text and code-point offsets are the verification contract

Every ingested document has exactly one **canonical text** — a UTF-8, NFC-normalized rendering produced once by the parser and stored as its own content-addressed object, referenced from `documents.canonical_text_sha256` — and every chunk is a **pair of Unicode code-point offsets into that text**, never a stored copy of it: `chunk_id = sha256(canonical_text_sha256 ‖ char_start ‖ char_end)` binds a chunk to its document and position, while `content_hash = sha256(chunk text)` keys embeddings and dedupe (identical boilerplate in two opinions shares a vector, not a row). Chunk text is not a Postgres column: the serving copy lives in OpenSearch `_source` (it needs the text for BM25 anyway; retrieval hydrates by id), Qdrant payloads carry only filter keys and the chunk id, and the **verification gate slices the canonical text in the content-addressed store by offsets — never the serving copy**. A re-parse that changes a document's canonical text yields new hashes and new chunk ids; nothing is edited in place. Greenfield-spec ticket 12, Aug 2026.

**Rejected:** chunk text as a column in the record (120–250 GB of derived text in Postgres and every backup, and a second copy to keep consistent with the offsets); byte offsets (they depend on encoding and break on the first non-ASCII section symbol); verifying quotes against the OpenSearch copy (a derived store must never be the thing verification trusts); chunk identity by content hash alone (boilerplate would collapse distinct positions into one row).

**Consequences:** verbatim span verification is a substring check — `canonical_text[char_start:char_end]` — rather than a judgment; the record plus the parser regenerate every index byte, which is what makes the derived indexes disposable (ADR-0012); transcript and Bates addressing for the Review and Transcribe branches attach to the same offsets through `pages` and `chunks` columns reserved now, so those branches never need a second addressing scheme; and a parser change is a corpus event (new canonical texts, new chunks, new generation), never a silent in-place edit.
