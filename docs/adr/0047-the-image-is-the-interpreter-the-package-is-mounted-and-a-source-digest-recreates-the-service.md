# The GIDEON image is the interpreter, the package is mounted from the tree that applied, and a digest of the service's declared sources is what recreates it

ADR-0045 moves General's turn into a GIDEON service, and general-turn ticket 01 is the first cycle to put GIDEON's own code inside a container, so two things with no precedent in the tree were settled at its claim (the maintainer's rulings, 2026-09-19). First, **the image carries the Python base and the pinned dependency set and no GIDEON code**: `images/gideon` is §17.1's one image — `gideon-api` its first role, `gideon-worker` its second when slice 3 brings it — and the service block bind-mounts `<checkout>/gideon` read-only, `<checkout>` being the tree that ran `apply` (`RenderInputs.checkout`, the input the systemd units already take): `/opt/gideon` on a converged box, the cycle's worktree during a proof. A box build is therefore due only when the base or a dependency moves, and `upgrade` and `upgrade --rollback` need no change, since the tree that applies is the tree that is mounted. Second, because the recreate rule sees rendered files and Compose blocks and never a mounted tree, **the block carries a label holding a sha256 over the service's declared sources** — `gideon/api/` today, a declared source being a package directory or a single module file — gathered with render's other inputs through the `Host` seam, recorded in the manifest's `inputs` block, and moving as a `changed compose block` for `gideon-api` alone. An AST tripwire holds every import in the declared sources, at any depth, to the standard library, the image's dependencies, and the declared set, and holds every import of a `gideon` module to module level, so nothing of the mounted tree loads lazily after `upgrade` has checked a new tag out under a running container; `gideon/__init__.py`, which `python -m gideon.api` runs from outside the digest, is held inert — a docstring and the one `__version__` assignment.

**Rejected:** baking the package into the image — every GIDEON release would then be a box build, a registry push, and a pin bump before it could run, `upgrade` would have to pull before it applied, and a proof from a cycle's worktree would need an image of its own; mounting the package but recreating on the release version instead of a source digest — the version file sits outside the service's sources, so a host-tooling release would recreate the service for nothing while a mid-cycle edit re-applied from the same worktree would be invisible, which is exactly backwards; hashing the whole checkout — a documentation or test edit would recreate a running service, and the recreate set is the thing `render --diff` asks a person to read before an apply; a runtime check of the mounted tree (an import-time version assertion, a watcher) — it would put the decision inside the container and after the fact, where the recreate rule already answers it before anything restarts; trusting review to keep the imports clean rather than a tripwire — a deferred import of a mounted module is invisible until `upgrade` swaps the tree under a live container, which is the one moment nobody is watching.

**Consequences:** the image's dependency set is the pin (ten `*_VERSION` build arguments with `pypi_project` watch entries), so a dependency moves through the Monday review's pull request like any other pin and the box rebuilds, while GIDEON's own code moves with the tag; `tools.imagebuild`'s build context and `inputs_digest` are unchanged, since no GIDEON source enters the build; a checkout unreadable to others leaves the service unable to import, which the healthcheck catches and `stack.logs_fix` explains; `upgrade --rollback` to a release before the service existed removes the container as an orphan; two cycles in flight on one box share the mount as they share the units — the second's apply swaps both to its own tree, and `docs/agents/on-box-proofs.md` §7's wait and `bin/worktree-remove`'s unit check cover it; the declared set is a list a later ticket extends, not a mechanism it rebuilds — ticket 06 adds `gideon/guardrail.py` in the release where the service first imports it, and ticket 11's split of that module into a package changes the entry and nothing else; and the tripwire's allowed names are the image's, so a declared source whose dependency is not yet in the image is a failing test and a ruling on ticket 06's plan, never a lazy import.
