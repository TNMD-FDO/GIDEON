# The dev seat keeps full passwordless sudo through General's launch: the seat is root and treated as root, stays out of the docker group, and narrows only when the box stops being the development box

The dev seat is the CSA account on the box from which every agent session runs, where the primary checkout lives, and from which the box's rendered units run; its sudoers drop-in grants it `ALL=(ALL) NOPASSWD:ALL`, chosen 2026-08-31 during bootstrap so agent sessions never block on root work, the risk accepted for a dev box holding no case data (bootstrap ticket 01). That ticket asked for a fresh ruling before `v0.2.0` puts General in front of the office's users, with their chats on the box, weighing four postures: full passwordless sudo, a session-unlock window, a scoped allowlist, interactive sudo. The facts the ruling rests on, taken on the box on 2026-09-08: every on-box step the workflow runs is root from a checkout or worktree the seat owns — `apply` and the release's apply, the on-box proof at every tag, `tools.turns`, `tools.acceptance` from the cycle's worktree, the contract tier under `sudo` — so a sudoers rule that runs code the seat can write is root-equivalent whatever command it names, and a rule that runs only root-owned code blocks the proofs, which run from the cycle's worktree by design (`docs/agents/on-box-proofs.md` §7); the box's sudo is sudo-rs (0.2.13 at the ruling), whose credential cache is a separate record per terminal session, and the harness runs each of a session's commands in a session of its own with no terminal, so a window (`timestamp_timeout`) unlocks nothing for an agent and every agent `sudo` would prompt where no prompt can be answered — for an agent the window posture is the interactive one; interactive sudo ends autonomous on-box work, every apply, proof, and harness run becoming a person's, typed outside the session; and the seat is not in the docker group, the contract tier running under `sudo` (slice-1 ticket 26), which keeps the seat's every root command in sudo-rs's log, where docker-group membership would leave none. The decision: **the drop-in stays, the seat is root and treated as root, and it stays out of the docker group.** What protects the box is the seat, not sudo: the seat's credentials; the harness's permission gate on what a session runs; sudo-rs's log of every command it runs; and the rebuildable box with its nightly backup (ADR-0035's clean-VM restore). The posture narrows when the box stops being the development box — a build box separate from the office's service box (slice-0 ticket 21's roles), or an install home at `/opt/gideon` with the proofs run on the acceptance VM — because then no agent session needs root on the box that holds the chats; or when a third account holds the seat's access. Bootstrap ticket 01, Sept 2026.

**Rejected:** a session-unlock window (sudo-rs keys its cache per terminal session, and the harness's shells are each their own session on no terminal); a scoped allowlist of `python3 -m gideon`, `python3 -m tools.*`, and `bash <script>` (root-equivalent from a tree the seat owns, and a rule bound to root-owned code stops the proofs); interactive sudo now (it ends the on-box proof the workflow makes at every tag, and the harness cannot answer a prompt); joining the docker group so the contract tier runs without `sudo` (root-equivalent, and unlogged).

**Consequences:** bootstrap ticket 01 is resolved and slice-1 ticket 18's person-run item is cleared on this point; no document promises a tightening at `v0.2.0`; a receiving office is unaffected, its operator's seat being its own and runbook 03's sudoers rule the acceptance runner's alone; the seat's root use is read from sudo-rs's log, not held by a narrower rule; the glossary carries the term.
