# One shared generator, sized by KV headroom, on its own GPU

GIDEON runs exactly one language model — the generator — and every branch (General, Research, and later Review, Draft, Transcribe) is a preset over it; Open WebUI's task model and the Research tool server's own LLM calls use the same engine. The model class is chosen by **KV-cache bytes per token and quality per resident gigabyte, not by parameter count**: at 20–30 concurrent users on one 96 GB GPU the binding resource is the KV pool, so a 27B hybrid-attention model (Qwen3.8-27B: 16 full-attention layers of 64, ~64 KiB/token at FP16, ~32 KiB at FP8, 262k native context) is preferred over a 70B dense model (~20 GB of KV left after weights, felt immediately as queueing) or a larger MoE whose tiny active set does not offset its resident weights. The generator owns GPU 0 exclusively; every other model — embedding, rerankers, later ASR and vision — lives on GPU 1 under per-service budgets.

**Rejected:** a separate small model for General and task calls (a second lockfile entry and a second thing to eval for no capacity gain); a second long-context deployment (the draft's "32k default + 128k Workspace model" was a KV-scarcity design; the hybrid architecture dissolves the scarcity and vLLM sizes the KV pool independently of `max_model_len`, so one deployment at the native window costs nothing until a request uses it); a 70B dense generator.

**Consequences:** a model swap is a hardware-profile change in `models.lock`, gated by the eval set and never by benchmark tables; presets and the tool server address the engine by a stable served name (`gideon-generator`) so a swap touches no preset; anything that would put a second model on GPU 0 (a resident VLM, an image model) is a redesign, not a config change; the serving engine and the precision are the ticket's decisions, not this ADR's, because both are reversible.
