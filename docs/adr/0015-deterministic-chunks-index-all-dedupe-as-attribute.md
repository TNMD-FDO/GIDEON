# Chunks are deterministic, structure-bound, and non-overlapping; every chunk is indexed; near-duplication is an attribute and collapse is a query

A chunk is a run of whole paragraphs inside one parser-typed section of the canonical text (target 512, hard max 1,024 tokens, never split inside a citation string), with no overlap between chunks, boundaries that depend on the parser alone, and an embedding computed from the bare slice — so chunk identity never depends on an embedding model, the same text always yields the same vector, and the `(content_hash, embedding_space)` ledger stays honest. Near-duplicate clusters (MinHash) and the boilerplate flag are computed at index build and stored as payload keys on every chunk; every chunk is indexed in both stores, and collapsing a cluster to one representative happens at query time (Qdrant `group_by`, OpenSearch `collapse`). Greenfield-spec ticket 13, Aug 2026; evidence in `docs/research/chunk-addressing-and-dedupe.md` (branch `research/chunk-addressing-and-dedupe`).

**Rejected:** semantic splitting — boundaries from embedding similarity make the chunk set differ per embedding model, so ticket 11's pre-bulk A/B would compare different corpora and a model change would re-chunk rather than re-embed (arXiv 2410.13070 finds no gain worth the cost); overlapping windows — one text in two chunks confounds content-hash dedupe, doubles vectors, and makes "which chunk was quoted" ambiguous (Chroma's first-party evaluation found no-overlap wins); late chunking and contextual retrieval — both make the vector depend on context outside the chunk, structurally incompatible with the ledger, and the saving they forfeit falls exactly on the boilerplate population the ledger amortizes, so their benefit is pursued *after* retrieval through neighbour expansion instead; indexing only the canonical member of a cluster — silently drops the variant that was the better hit for a query, and Qdrant's own capacity formula puts index-all at ≈ 36–86 GiB (25–60 M chunks), so RAM never forces it.

**Consequences:** a parser or chunker change is a corpus-lockfile event (new chunk ids, new generation); the embedder never sees a prepended header by default (E10 tests one, and a win would re-key the ledger and forfeit the boilerplate-shares-one-vector saving); the stage-1 reranker always sees a whole chunk; deep pagination through grouped vector results is not available from Qdrant (`group_by` has no offset) — a turn consumes the top-limit groups, and any page-through UI is served by the lexical leg; matter chunks cluster within one tenant only, never across.
