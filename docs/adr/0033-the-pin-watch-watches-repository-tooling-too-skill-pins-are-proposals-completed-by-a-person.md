# The pin watch's subject includes the repository's development tooling; a skill-source pin is a proposal a person completes on its branch, and a tripwire holds the records to the folders

ADR-0031 scoped the pin watch to "every component a release runs". The development lifecycle this repository ships to every CSA is vendored the same way a release component is — 14 TRIP-workflow skills pinned to a release tag and 25 Matt Pocock skills tracking upstream `main`, recorded in `skills-lock.json` with GIDEON's own rules confined to marked blocks and TRIP-init slots (`docs/agents/tooling.md`) — yet nothing noticed when either source published, and nothing failed when a vendored skill was edited outside a block or slot, an edit the next upgrade silently discards. The `skills` CLI cannot hold the line itself: its `update` reinstalls every lock entry unconditionally, it lowercases directory names, and it installs a branch's head, never a commit. **The decision: the pin watch's subject widens from what a release runs to what the repository vendors, with one pin per skill source — the latest TRIP-workflow release against the lock's `ref`, the head of `mattpocock/skills` `main` against the commit recorded in the tooling document — and both are proposals the watch never completes: a pull request bumps the record only (never a file under `.claude/skills/`), a person completes it on that branch by the document's recipe (a three-way merge of GIDEON's delta for TRIP, a CLI run proven against a clone at the recorded commit for Matt Pocock), and the watch never pushes to a branch that carries a person's commits, whatever upstream did since. A stdlib tripwire in the hosted `checks` job is the guard that the records and the folders agree: every lock entry's folder hash recomputed with the CLI's own algorithm, the customized skills' blocks checked against the document's table, and the lock's TRIP `ref` held to the document's provenance line — so a TRIP proposal is red until a person completes it.** Slice-0 ticket 18, Sep 2026.

**Rejected:** the CLI's own `update` (it reinstalls every entry with a `skillPath` and discards the delta); the watch running the CLI on the proposal branch (a TRIP upgrade is a merge with human conflict resolution, and a Matt Pocock refresh is an install a person must prove against the commit it names, since the CLI clones with `--branch` and cannot pin a commit); installing Matt Pocock at an exact sha (the same CLI limit); a GitHub issue or a tracker ticket as the notice (the tracker is human-curated, and the pull request already carries the state table — opened, updated, declined, closed, completed); a monthly human check of the release pages (ADR-0031's rejection stands); superseding a person's completion when upstream moves again, as a built-image proposal allows (a rebuild is regenerable on the box; a resolved three-way merge is not).

**Consequences:** the Monday review can show two more pull requests, each carrying its recipe; a TRIP proposal is red on the hosted checks by design until the lock and the provenance line agree, the same signal a built-image proposal gives; a Matt Pocock proposal is green from the start, because no hosted check can tell a branch-tracking install from the commit it names — the recipe's clone check is the guard, and a record that lags upstream by one commit is corrected by the next proposal rather than left wrong; the provenance sentence in `docs/agents/tooling.md` §2 is a machine-read record on one line, refused by the tripwire when its shape breaks; the upgrade recipes run on the watch's branch when its pull request is open, and a branch with a person's commits is left to that person, its pull request's title kept truthful to what the branch holds; the lock-coupling rule (ticket 13) covers the skill records, so no test types the TRIP `ref` or the recorded commit; and every later vendored source is one more pin of the same shape.

**Amended 2026-09-20 (`v0.2.23`, standing ticket 19):** the consequence that a branch with a person's commits is left to that person rests on a commit count, `origin/main..origin/<branch>` above one, and that count is true only over a complete history. The hosted runner's checkout is depth 1, so from the first run after `main` left the branch's base the count was the branch's whole fetched ancestry: the first live Matt Pocock proposal (pull request 5) read `completed` on every run from the day after it opened though only the watch had committed there, and it was never refreshed while upstream moved on. The protection failed safe in the direction this decision cares about — no person's work was overwritten — and failed silently in the other, a proposal nobody had touched left stale under a row that said otherwise. The watch now completes a shallow checkout in its one fetch before anything is counted, held by a test, so the rule holds wherever the watch runs and on no workflow line. The decision itself is unchanged.
