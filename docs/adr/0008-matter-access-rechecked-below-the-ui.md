# Matter access is re-checked below the UI, with Open WebUI as the authorization oracle

Open WebUI's group RBAC decides which knowledge bases a user can attach to a chat, and it is additive-only, has no deny rules, and has already shipped one authorization bypass in exactly the conflicts-wall shape (CVE-2026-45398: retrieval endpoints skipped the knowledge-base check). GIDEON therefore treats the UI check as intent, not enforcement: the retrieval service refuses any request that names a knowledge base without a user identity, and re-checks every knowledge-base id by asking Open WebUI itself — the Research Pipe forwards the caller's session token, the service calls `GET /api/v1/knowledge/{id}` as that user, and only HTTP 200 permits. No authorization rule is replicated in GIDEON's own code or tables, so nothing can drift from what the user sees in the UI; every denial is logged and alerted as a conflicts-wall incident.

**Considered and rejected:** trusting the UI check alone (charting's position; refuted by the advisory); an in-Pipe call to Open WebUI's internal `has_access()` (couples to internal Python API across upgrades — kept as the documented fallback if token forwarding breaks); a service-side ACL layer with its own tiers, tables, and a physically separate `matters_restricted` collection and credential (draft 5's design — replicates the rule, drifts, and adds isolation that enforces nothing the oracle check does not already). **Consequences:** the Pipe→retrieval-service contract carries a user token that is held in memory per request and never logged or cached; screened matters are ordinary knowledge bases shared with named users, not a separate store; Open WebUI's REST API becomes a runtime dependency of retrieval, so an Open WebUI outage fails retrieval closed rather than open.
