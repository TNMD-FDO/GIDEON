# Improvement loops propose; only a person's explicit act changes what GIDEON answers

GIDEON gets better through **improvement loops**: automation observes and proposes, and a person decides and acts. The decision, ruled at the improvement effort's split on 2026-09-21: **nothing automated changes what GIDEON answers.** What GIDEON answers means the pinned configuration (the retrieval and research configs, prompts, the guardrail's patterns and seeds), the models, the eval set version, and the promoted index generation. A change to any of these is a person's explicit act, and only two acts count: a merged pull request followed by a tag, or a person's `index promote` after the gates pass. Corpus cuts float free of tags (§22.2), so the rule is about the act, not the tag. Automation's output is a **proposal**, and a proposal changes nothing until someone acts on it. This is ADR-0017's "defaults first, then measure" and ADR-0023's "the judge never gates," extended from single decisions to the standing machinery that proposes them. The pin watch already works this way for pins.

Four rules follow from it:
- **Proposals stay on the box.** They're read through `gideon proposals` and the Eval board. The only notice that goes out is a weekly, figure-free count through the office SMTP relay. Automation writes no ticket, no pull request, and no committed file. Figures derived from users' turns would be a new kind of egress, the box would need a standing write credential for the repository, and a bot on `main` would be a writer no tracker session coordinates with.
- **The trigger registry is committed release content.** A trigger's state (`watching`, `acted`, `retired`) moves only by a pull request, so the developer's ruling on a proposal is in git history, and every office receives the same registry with its release.
- **Product loops run on the build box.** The trigger watch and the challenger run behind the `build-box` marker, and the developer rules on them. **Office loops** (the feedback packet, the demand map, the guardrail review) run on every box and serve that office alone.
- **A feedback turn's text is read by a person on the box and nobody else.** No development session reads it (§0.1 rule 2), and a candidate eval case enters the repository only as text a person wrote and signed. Redaction can't remove matter facts from a legal question, because the facts are the question. For the same reason, a kept-event row stores what an out-of-corpus object resolves to (a court id, a type, a source key), never the citation text the user typed.

**Rejected:** online learning from ratings, and bandit or per-user configuration switching, because the same question would get different evidence at different times, which §12.7 already refuses; automatic promotion of a challenger or a generation whose gates pass, because a gate is a floor, not a judgment that the change is wanted; automatically rewritten prompts, because the eval would slowly come to measure itself; bot-opened pull requests or tickets from the box, for the reasons in the first rule; automatic generation builds on an upstream notice, because hours of store load and disk are the CSA's to schedule; and figures flowing from a receiving office back to the developer, because before 1.0 there is no such office and the consent design doesn't exist (reconsidered at 1.0, `.out-of-scope/cross-office-feedback.md`). The whole family of rejections is `.out-of-scope/self-tuning-answers.md`.

**Consequences:** every loop is slower than a self-tuning one by at least one person's review, and that's the intent. An office's CSA sees only the proposals they can act on. A trigger that no on-box row can compute (a CVE, a person's report) is a standing ticket, not a registry entry. Learned components, such as a fine-tuned reranker or learned fusion, aren't a loop: they're a trigger whose firing proposes opening their own effort, held out on a split the eval never trains on.
