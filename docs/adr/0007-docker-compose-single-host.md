# Docker Compose on a single host; no Kubernetes until a second node exists

GIDEON runs as one Docker Compose project (rootful Docker Engine + Compose v5) on one server, operated by two CSAs. Kubernetes (including single-node k3s), Podman/quadlet, and Swarm were considered and rejected: on a single box with two GPUs and sixteen mostly stock services, an orchestrator adds a control plane, a networking model, and a vocabulary to learn without adding any capability the product uses, and Compose is the form every engine image, Open WebUI's own docs, and a receiving office's CSA already understand. Every downstream artifact — the release (`compose.yaml` + rendered configs), the installer, the acceptance test, the restore drill — speaks Compose.

**Consequences:** the release is not portable to a multi-node deployment without a redesign; this is accepted, and the boundary is explicit: Kubernetes is reconsidered only when a second GPU node physically exists. Things a cluster would have provided are done the plain way instead — the restore drill's scratch instance is a second Compose project on the same host (`gideon-drill`), the CI runner is a host systemd service, the local image registry is a Compose service bound to loopback. GPUs reach containers through the NVIDIA Container Toolkit's CDI path, assigned by GPU UUID. Greenfield-spec ticket 08, Aug 2026.
