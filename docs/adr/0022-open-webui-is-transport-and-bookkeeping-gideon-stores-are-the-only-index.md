# Open WebUI is file transport and knowledge-base bookkeeping; GIDEON's stores are the only index Research reads, fed by the extraction hook and a frontend reconcile

Every file a user uploads into GIDEON — into a matter knowledge base or as a chat attachment — reaches GIDEON through Open WebUI's external content-extraction hook (`CONTENT_EXTRACTION_ENGINE=external`, `PUT /process`, bytes + filename + bearer), and that hook is the **write path into GIDEON's own stores**: the ingestion service writes the original and the canonical text to the content-addressed store, the record to Postgres, and the chunks to Qdrant and OpenSearch under the matter's tenant key, then returns the canonical text to Open WebUI only so its file record and preview are truthful. Open WebUI never chunks, embeds, or retrieves anything for Research: `BYPASS_EMBEDDING_AND_RETRIEVAL` is on, the Research model preset ships with **File Context off**, the Research Pipe forwards knowledge-base and file ids to the Research service and refuses a turn in which the frontend injected document text, and the service reads only GIDEON's indexes. Because the hook carries no user, file, or knowledge-base id, the binding of a document to its matter is learned by a **frontend reconcile** — a periodic read of Open WebUI's own `file` / `knowledge` / `knowledge_file` / `chat` tables through a read-only role, keyed by the byte hash both sides compute — and never from the extraction call. Draft 2 §3.2 called this the shadow-index posture; every retrieval decision since (ADR-0008, ADR-0013, ADR-0014, ADR-0015, ADR-0018, ADR-0019) silently assumed it, and this record makes the assumption explicit so nobody "fixes" uploads by turning Open WebUI's native RAG on. Greenfield-spec ticket 20, Aug 2026; Open WebUI v0.11.0 behaviour verified against the tagged source and recorded in the ticket.

**Rejected:** enrich-in-place (draft 2's posture A — Open WebUI's chunker cannot produce code-point offsets into a canonical text, so the verification gate, anchors, dedupe attributes, and the tenant re-check would all have to be rebuilt on its terms, and its vector store is the one a UI-level bug has already exposed, CVE-2026-45398); File Context on for Research with the Pipe stripping injected text (the gate would see text it never retrieved, and a preset toggle would silently change what the answer is grounded on); Open WebUI's "external knowledge" connections (a read-only knowledge base backed by a direct vector-database connection using Open WebUI's own embedding and similarity search — not a retrieval contract, and the Pipe bypasses native retrieval anyway); learning the binding from Open WebUI's outbound webhooks (correct, but a second channel — an endpoint, an installer registration, a payload contract, and a retry question — whose only benefit is shortening a 30-second reconcile lag; recorded as an optimization with a trigger, not a design); polling the REST API with the break-glass key (the same schema coupling plus a root-equivalent credential in a service).

**Consequences:** Open WebUI's per-file `pending → processing → completed | failed` status tracks GIDEON's pipeline for free because the hook returns only when the document is retrievable; the frontend's copy of each original and canonical text is a second copy deleted with the file; four Open WebUI tables are a contract GIDEON tests on every frontend pin bump; a matter document is bound to its knowledge base within one reconcile interval of being added, and unbound within one interval of being removed; and the only Open WebUI features Research depends on are auth, the file upload, knowledge-base sharing, the extraction hook, and the Pipe/event API.
