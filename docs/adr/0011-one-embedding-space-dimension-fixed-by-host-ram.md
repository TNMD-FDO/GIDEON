# One embedding space, its dimension fixed by host RAM

GIDEON embeds every corpus chunk, every uploaded document, and every query in exactly **one embedding space** — one model and revision (Qwen3-Embedding-8B), one output dimension (1024, Matryoshka-truncated), one precision, and one query-side-only instruction convention — pinned in `models.lock`; the embedding space is a property of an **index generation**, and changing any part of it means building a new generation beside the live one and swapping it in whole, never editing in place or mixing spaces. The dimension is fixed by **host RAM, not disk**: sub-second search over 25–90 M chunks needs the quantized vectors and the HNSW graph resident, and on a 251 GiB box sharing memory with the lexical store and Postgres roughly 100–120 GB is available — 1024 d int8 fits (~61 GB at 60 M), 1024 d fp16 is marginal, 2560 d does not fit, while every candidate's *disk* footprint fits the 12.8 TB with room for a rebuild. Instructions live only on the query side so that no instruction change can ever force a re-embed.

**Rejected:** native dimensions (2560/4096) with fp16 storage — no RAM for them, and no quality evidence that beats MRL truncation; mixing an old and a new embedding space in one index during a migration (scores are not comparable across spaces, so the index would silently rank by model identity); per-document instructions (they would bind the corpus vectors to an instruction string); a second embedding model for uploads or for the Open WebUI-native path.

**Consequences:** a change of embedding model, dimension, precision, or pooling is a multi-week re-embed (≈ 1–3 weeks for the pilot corpus on the 8B, 2× faster on the 4B), so it is decided by the eval set on a corpus sample *before* a bulk run, never after; every embedding client — the bulk job, the ingestion service, Open WebUI's native path — must land in the same space, so the embedding server itself defaults to 1024 d and the instruction is applied at exactly one layer per client; the vector store must hold fp16 originals for rescoring and int8 for search; the model choice (8B vs 4B vs 0.6B) and the serving engine are the ticket's reversible decisions, not this ADR's.
