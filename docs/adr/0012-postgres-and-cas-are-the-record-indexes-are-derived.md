# Postgres and a content-addressed store are the record; Qdrant and OpenSearch are derived indexes

GIDEON's data layer is three stores with one rule. **The record** — what a backup must protect and what everything else is rebuilt from — is one PostgreSQL 18 cluster (two databases: `gideon` for GIDEON's schema, `openwebui` for Open WebUI's) plus a **content-addressed store** on the XFS data volume (`/data/bulk/cas/<aa>/<bb>/<sha256>`: uploaded and downloaded originals and each document's canonical text, immutable, named by hash). **Qdrant** (int8 scalar-quantized search vectors and HNSW resident in RAM, fp16 originals on disk, oversample-and-rescore; indexed payload keys for court / date / precedential-status / tenant pre-filtering) and **OpenSearch 3.x** (BM25, exact-phrase and span queries over chunk text) are **derived indexes**: nothing exists only in them, every write to them is a replayable job from Postgres, and losing one costs a rebuild, never data. The job queue is Procrastinate on the `gideon` database (`FOR UPDATE SKIP LOCKED`), so job state and job output are always restored to the same point in time. Greenfield-spec ticket 12, Aug 2026.

**Rejected:** **pgvector** in place of Qdrant — it has no int8 storage; fp16 `halfvec` resident is ~123 GB at 60 M chunks × 1024 d and ~184 GB at 90 M against the ~100–120 GB the host can give vector serving (ADR-0011), and binary quantization is an experiment (E3), not a default; it would also put 150–250 GB of derived vectors inside the record database and its backups. **OpenSearch k-NN as the only vector store** (drop Qdrant) — feasible on paper (`mode: on_disk`, 8-bit, rescore), but 60–90 GB of quantized vectors and the HNSW graph would be off-heap memory in the same JVM whose page cache the lexical index needs, governed by a circuit breaker re-tuned as the corpus grows, and one process's failure would take both retrieval legs; two independent memory budgets won. **Everything in Postgres** (pgvector + ParadeDB `pg_search`) — the same vector problem plus a young AGPL extension carrying the load-bearing citation search with no evidence at 60–90 M rows and no alias-swap equivalent; a revisit-in-a-year option if GIDEON wants to shed a service. **MinIO / any S3 service** — MinIO's community edition was archived in Feb 2026, and no GIDEON client needs an S3 API. **Redis** as the queue — a service and a backup target whose state cannot be restored consistently with Postgres. **Elasticsearch** — its AGPL option is source-only (shipped images stay Elastic License v2) and its tiering gates features; nothing to prefer over an Apache-2.0 engine.

**Consequences:** the backup set is Postgres (both databases) + CAS + configuration, backed up **CAS first, then Postgres**, so every row that names an object finds it (extra objects are harmless; the reverse is a loss); Qdrant, OpenSearch, `/data/work`, raw corpus snapshots, and model weights are excluded as reproducible. Index generations (ADR-0011) exist in both derived stores under the same names and are promoted by one command that flips both aliases and the Postgres record together. A future graph store for citation traversal or a GraphRAG layer needs no topology change: the citation graph's record is the normalized `citations` table in Postgres (recursive CTEs serve depth-limited traversal at tens of millions of edges), so a graph engine, if ever needed, is one more derived index rebuilt from Postgres, and generated summaries are documents in the same stores and the same embedding space.
