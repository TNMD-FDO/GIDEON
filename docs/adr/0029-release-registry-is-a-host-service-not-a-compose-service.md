# The release registry is a host service that predates the Compose project

ADR-0007 and spec §20.1 placed the local image registry inside the Compose project ("a Compose service bound to loopback"); ticket 02 landed it as a provision-owned systemd unit, and ticket 04's discovery settled where it lives: **on the host, converged by `gideon host provision`, before any Compose project exists**. The reason is bootstrap order, not taste: `gideon apply` pulls every image in `images.lock` — Caddy first — from the release registry, so the registry cannot be one of the services that pull depends on; it must be up, serving digests, before the first `docker compose up`, and it must survive every `apply`, `upgrade`, and Compose teardown untouched. The one image the release registry never serves is therefore its own (`registry:3`, pinned by digest in `host.lock` and pulled from Docker Hub during host provisioning — the host-provisioning egress group names those hosts). Slice-0 ticket 04, Sep 2026; supersedes the registry line of ADR-0007's consequences and §20.1's `registry` row.

**Rejected:** defining `registry` in `compose.yaml` and special-casing it in apply (pull it from Docker Hub directly, start it alone, then pull the rest) — two pull paths and an ordering rule inside the one command that is supposed to be uniform; keeping both a provision step and a Compose service — two owners of one port.

**Consequences:** `images.lock` never lists the registry image; `registry gc` and the backup of `/data/registry` are host-level concerns; the acceptance VM reaches the registry on the libvirt bridge through a host-published port (with the `DOCKER-USER` rule the firewall step owns); moving to GHCR at 1.0 changes the site `registry` key and nothing in the Compose project.
