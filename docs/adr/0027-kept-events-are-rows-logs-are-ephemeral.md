# Kept operational events are rows; logs are ephemeral; no log store or tracing platform in v1

Anything GIDEON must keep about its own operation — a guardrail trip, an abstention, a conflicts-wall denial, a per-turn gate report, a backup or drill run, an audit row — is written as a content-free row in Postgres, partitioned by month and dropped after a year, and read by Grafana through a read-only role. Container logs are debugging scratch: they go to systemd-journald (surviving container recreation at every upgrade, searchable by time, expired by a time setting) and are never the place a fact of record lives. Metrics are Prometheus time series; alerts are Alertmanager rules delivered by email. That is the whole observability tier: Prometheus, Alertmanager, Grafana, and exporters. Greenfield-spec ticket 22, Aug 2026.

**Rejected:** a log store (Loki plus a collector — two more containers and a query language whose real gain over journald is a search UI; revisit in a later version); an LLM tracing platform (Langfuse v3 needs its own Postgres, ClickHouse, Redis, and an S3 store — five containers and a second database technology for a per-turn waterfall that the `turn_log` row already carries in numbers; Phoenix is one container but the same answer); Open WebUI's OpenTelemetry (off — its outbound HTTP-client spans carry the SearXNG search URL, and so the user's search text); a single-binary replacement for Prometheus and Alertmanager (VictoriaMetrics' `vmalert` has no notification receivers; Alloy is a collector only).

**Consequences:** every question of the form "what happened, how often, since when" is a SQL query or a Grafana panel over rows that are already backed up with the record, and the audit log is one of those tables — append-only, ids only, never text; nothing that must be kept depends on a log line surviving; the revisit trigger for a tracing platform is stated — a CSA cannot answer "why was this turn slow or wrong" from `turn_log` plus the journal — so the decision is measured, not argued.
