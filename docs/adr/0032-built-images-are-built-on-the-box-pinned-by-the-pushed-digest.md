# GIDEON-built images are built on the box from the mirrored base, pinned by the digest that was pushed, and moved only by proposal

A release's images were all upstream's until pgBackRest forced the first exception: Postgres runs its archive and restore commands inside its own container, so the binary has to be in the Postgres image, and no official image carries it (spec §19.1, §20.1 — spec bug (v) on slice-0 ticket 16). That made "how does GIDEON build an image" a decision rather than a detail. Container builds are not byte-reproducible — apt writes timestamps, layers carry build times — so the image lock cannot state a built digest the way it states a mirrored one. **The decision: a built image is built on the box by a repository tool, from the release registry's mirrored copy of its pinned base, and the lock records the digest the push produced, beside a digest over the build inputs (base digest, build arguments, Dockerfile bytes) that the hosted checks recompute; a bump to any input — noticed by the pin watch like every other pin — is a proposal a human completes by rebuilding on the box and committing the recorded digests on the proposal's branch, and the watch preserves that commit rather than regenerating over it.** The image's Dockerfile carries no version: every input reaches it as a build argument from the lock, so a pin lives in one place. Slice-0 ticket 16, Sep 2026.

**Rejected:** reproducible builds (a project of its own — pinned build epochs, rewritten timestamps, an archive of every package ever installed — bought nothing the release needs, since a lock that records the registry's bytes already lets `apply` verify what it pulled); rebuilding in CI on merge or on tag (the digest must be in the lock before the tag, and a hosted runner cannot push into the loopback registry that holds every pre-1.0 digest); a third-party pgBackRest image (ticket 22's ruling stands, and it would not put the binary where Postgres calls it); a pgBackRest sidecar sharing the volume with a hand-rolled WAL spool between it and Postgres (the same spool would have to be mirrored by a hand-rolled restore command on the point-in-time path — two non-standard mechanisms on the one path a disaster exercises).

**Consequences:** the release registry, not the repository, is where a built image exists — `/data/registry` is in the backup set for exactly this reason (§2.4), and after a registry loss the image is rebuilt or restored, never recovered from git; a proposal pull request on a built pin is red on the hosted checks by design until the rebuild lands, which is the record that upstream moved and the work is not done; the order build → record → commit → merge is a rule people follow, with the inputs digest as the guard when they do not; post-1.0's "pushed by CI on tag" is a copy of the pinned digest to the public registry, byte-for-byte, not a rebuild; and every later GIDEON image (`gideon-api`, `gideon-worker`) is one more built pin with the same lifecycle.
