# Query planning is bounded: deterministic extraction first, one schema-constrained model call, model filters narrow a leg and never the pool, no model-written queries against the record

Before any model sees a Research question, deterministic code extracts its exact objects — reporter citations (eyecite), statute sections, Guidelines ids, rule cites, docket numbers (a versioned GIDEON regex grammar), and party names present verbatim in the user's text — and turns each into a verbatim lexical retrieval leg that no later step can remove or respell. Then exactly one generator call, thinking off, temperature 0, output constrained to a JSON schema whose filter values are enums of the collection vocabulary, returns a query plan: an intent (the route), up to four standalone sub-queries, an optional step-back rule query, optional narrowing filters, and optional calls to named parameterized tools. Filters from user interface state (tenant, collection set) are the floor nothing overrides; a jurisdiction the user names is a hard filter on every leg; the model's narrowing applies to one additional leg only. The plan call has a timeout and a fallback (deterministic legs plus the raw message), so retrieval never depends on the model behaving. Greenfield-spec ticket 14, Aug 2026; evidence on eyecite's query-side coverage in `docs/research/eyecite-query-side-coverage.md` (branch `research/eyecite-query-side-coverage`).

**Rejected:** a purely deterministic query layer — compound and fact-heavy doctrinal questions make poor BM25 and mediocre embedding queries, and the harvest is full of them; an agentic loop (the generator retrieving until satisfied) — unbounded time on the one shared GPU, non-deterministic across eval runs, undebuggable by two CSAs; HyDE — *deferred, not rejected*: a hypothetical legal passage is invented law with invented citations steering the dense leg, the instruction-aware embedder already bridges the question↔passage gap, and it is a second free-text generation per turn (revisit trigger recorded in the ticket); LLM datastore routing — an LLM choosing to skip `authorities` for "does § 3663A apply to § 2243 convictions" is a silent recall loss nobody would see, while querying three collections costs milliseconds; semantic routing — there is one Research preset, nothing to route among; text-to-SQL / text-to-Cypher — model-written queries against the record are an injection and consistency surface and violate the spirit of ADR-0006 (deterministic code or nothing), so structured questions go through a fixed list of named tools whose arguments are extracted objects; a default hard jurisdiction filter from site config — nine of forty harvested questions are nationwide by design and would be answered wrong silently, so home jurisdiction is a controlling leg that guarantees controlling authority is in the pool without excluding anything; `precedential` as a filter — users cite unpublished opinions constantly, so it is a label and a ranking weight.

**Consequences:** the retrieval service, not the Pipe, owns the query layer, and every retrieval response carries provenance (plan mode, objects extracted, out-of-corpus objects, filters applied by tier, legs run, tools called) that the Pipe renders as a status line, so a wrong filter is visible to the attorney; retrieval is stateless per turn and the plan call sees only user-authored chat history, never retrieved document text; a name the model supplies becomes a lookup leg only if it appears verbatim in the user's messages — model knowledge flows through sub-query text, never through lookups; the number of legs per turn is bounded (≤ 4 sub-queries + rule + controlling + narrowed + exact-object legs), so ticket 15 sizes the candidate pool per leg; the `jurisdiction` site key is the first retrieval-stack key on the map; `query_plan: off` is a release-artifact kill switch whose path is the eval baseline; every LLM-touching piece has a named experiment and a metric.
