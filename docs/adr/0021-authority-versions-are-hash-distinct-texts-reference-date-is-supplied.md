# Authorities are versioned as hash-distinct texts with effective ranges; the reference date is supplied, never derived

Statutes and Sentencing Guidelines change under the reader and the change is invisible in the text, so GIDEON keeps **every version** of every authority it ingests: one row per statute section or guideline per **distinct text** (content hash), with the date range it was published as current — a US Code section has a handful of rows across 383 release points because almost nothing changes between two of them, and a verbatim reprint (the 2021 Guidelines Manual) adds none. Beside the versions sits a second record, **amendment events**, taken from the authority's own history notes (USLM `<sourceCredit>` and amendment notes, the Guidelines' per-guideline Historical Notes) rather than from the text diff, because mid-cycle amendments that were never published as an instrument have dates but no text; the diff is the agreement check on the notes, never a second source. Retrieval selects a version by one **reference date the user states in the question**: without one, only current versions are retrievable and every answer says so; with one, the version in force on that date and a label of what has changed since. GIDEON never decides which date governs — USSG §1B1.11 selects the manual in effect at sentencing unless that would violate the Ex Post Facto Clause (*Peugh v. United States*, 569 U.S. 530 (2013)), which is a comparison, not a lookup, and statutes turn on offense or filing dates by a further legal reading — so the attorney supplies the date, exactly as a person, not GIDEON, computes a deadline (ADR-0006). Greenfield-spec ticket 19, Aug 2026.

**Rejected:** encoding §1B1.11 in code (take offense and sentencing dates, pick the edition, flag the conflict) — "harsher" is analysis carrying a machine's authority; the drafts' "filter by offense date" — wrong in the ordinary case, where the sentencing date governs; one document per title per release point — 383 near-identical copies of every title and duplicate hits; a per-user date setting in the frontend — persistent, so a date set for one client silently applies to the next, the very staleness the design exists to remove; refusing to answer without a date — none of the forty harvested questions carried one.

**Consequences:** the version table answers "what did § X say on D" and the event table answers "when has § X changed", and a date inside a gap between a mid-cycle amendment and the next published manual returns the last published text with a label naming the gap; identifiers outlive their text (repealed sections and consolidated guidelines keep their last version, with a successor where one exists); statute history reaches back to 2013 in USLM XML and to 1994 through the annual archives at section granularity, with subsection anchors best-effort and un-pinciteable where unresolved; the reference date filters authorities only, never caselaw, so a later opinion construing an older text is always in the pool and a dated Guidelines pool is one manual in its entirety by construction; nothing here is a site setting — the horizon is a corpus-lockfile fact, the labels are product text, and the only "off" state exists for the evaluation baseline.
