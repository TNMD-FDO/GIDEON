# Backup, restore, install, and upgrade — architecture leaf

**Read this when** implementing backup, restore, install, upgrade, or rollback; the owning modules are `gideon/host/backup.py`, `gideon/host/backupset.py`, `gideon/host/restore.py`, `gideon/host/drill.py`, `gideon/host/install.py`, `gideon/host/upgrade.py`, and their tests. The map is [`../ARCHI.md`](../ARCHI.md); its §8 table names every command's leaf.

## Commands

- **`backup run [--full] [--label]`** (§19.1, ADR-0026; `backup.py` over `backupset.py`): `intent` → `files` (each root of `backupset.inventory_roots` as a hard-linked snapshot under `sets/<label>.partial/`) → `secrets` (`tar | age`, no plaintext on disk, sealed to the office recipient and the box's own — derived by `age-keygen -y` from the root-only identity, whose absence, custody drift, or undecodable content refuses before any stage — both named in the manifest's `recipients`, the singular `recipient` still written for a previous tree; the keyed fingerprint; and the ids the making host's `gideon` account has, read once at the preconditions through the seam and refused there when the account is absent or malformed, written as the manifest's optional `gideon_ids`) → `postgres` (full or incremental; then the **archive boundary**: the instant before pgBackRest's `check` confirms a WAL switch becomes the manifest's `archive_through`) → `counts` → `manifest` (written last, then the set renamed from `.partial`) → `prune` → `applied`. Labels: UTC timestamps, `pre-restore-<ts>`, or an operator's `pre-<tag>`.
- **`backup push [--verify-all]`** (§3.7): `push.json` (the newest set and its `archive_through`) written into staging first, so every remote snapshot carries its coverage record; one rsync over SSH (`sshtarget.py`) into `<label>.partial/`, ownership not sent; rename; prune by age; then **the off-box check** — the mandatory files plus a deterministic sample of every root (`--verify-all`: every file) hashed on the target; one `backup_push` row.
- **`restore --from staging|target [--at | --set <label>]`** (§19.2, ADR-0005; `restore.py`): `select` (by time or by set label; from the target, the oldest snapshot whose `archive_through` covers `--at`) → `pre-restore` (a full set, only when the whole stack is running and its staging holds a set; a fresh stack — `sets/` absent or empty — skips the stage whole, its row the constant `FRESH_STACK_SKIPPED_DETAIL`; a staging of incomplete entries alone refuses) → `fetch` (target only, into a side directory; the restoring host's own `gideon` ids are read by name at the preconditions and refused there) → `verify` (every root held to its manifest exactly, then pgBackRest's own `verify`) → `stop` (the stack and, on the build box, the host registry) → `swap` (rolled back on failure) → `files` (both re-owning stages map through one pure `OwnerMap` per set, built from that set's `gideon_ids` and the host's: a recorded uid becomes the host's, a recorded gid the host's, each independently, every other id passing through, and a set carrying no record is the identity, its rows saying so and its `next` line naming `host provision` before the apply) → `postgres` (a delta restore to `--at`, else the set's boundary, promoting; **a named set restores from its own backup on its own timeline**, because after a rollback the auto-selected backup sits on a diverged timeline) → `stores` (the `restore` row; the host registry starts only on the build box) → `next` (frontend and ingress left down; whether the secrets on disk are the set's; then `apply` and `backup run --full`). **Nothing live stops before the whole source has verified; an undeclared host with an active registry refuses before any stage.**
- **the backup lock** (slice-0 ticket 26; `backuplock.py` over the seam's `LockingHost` pair): `backup run`, `backup push`, and `restore` each take one exclusive `flock` on `/run/gideon/backup.lock` (the directory 0700, the file 0600, root's alone; tmpfs, outside the staging `swap` moves) after their root and clock checks and hold it to the run's end, the kernel dropping it however the holder ends and the file never unlinked. The holder writes a one-line record — command, pid, the run's clock — that a refused taker prints before any stage, exit 1, the nightly's unit failing; an empty or malformed record refuses too. A take whose record carries this process's pid is **nested** and passes without releasing: `restore`'s pre-restore run and push. `install`'s `backup` phase and `upgrade`'s and `--rollback`'s safety runs take and release it around their in-process `backup run` and hold nothing across their stages; the rollback's `restore` child takes it in its own process; the drill takes none.
- **`backup drill`** (§1.8, [22]; `drill.py`): the pure `render/drill.py` document written to `/data/drill/compose.yaml` — project `gideon-drill`, Postgres over the read-only repository, the frontend on loopback with the production `env_file`; `prepare` → `tarball` (the hash, and exactly as many X25519 stanzas as the manifest names recipients) → `verify` → `postgres` (an immediate restore of the newest set's backup) → `counts` → `frontend` (healthy means its migrations ran clean) → `cas-walk`/`retrieval-read` (`inert` until slice 3) → `teardown` in a `finally`; one `backup_drill` row.
- **`install`** (§3.6 step 5; `install.py`): a data table of phases over the existing runners in-process — `preflight` → `apply` → `reconcile` → `engine-verify` (the gate: `engine verify` in-process behind its `observe` seam, a fresh child namespace carrying the observer; the phase row reads the one skipped row on a no-GPU host — `ENGINE_VERIFY_SKIPPED_DETAIL`, which the acceptance harness requires — `completed (<n> checks ok)`, or `refused (exit <n>): <the failed rows>` with the do-not-go-live fix, the run stopping there) → `backup` → `drill` → `audit` → `url` — one phase row after each nested command's own rows, the fix naming the nested command to run by hand. The `install` row's `intent` is written once apply has converged the stores, then `applied` or `failed`; the URL is the last line.
- **`upgrade <tag> [--acknowledge-breaking]`** (§3.6 step 7, §2.1; `upgrade.py`): runs from the current tree and, after the checkout, hands over to the new tree's own CLI as passthrough children; the module has no function-level import, so nothing of the new tree is loaded into the old process. `preconditions` (a clean checkout; every git call runs as the checkout's owner) → `fetch` → `version` (a lower tag refuses naming rollback; a major cross refuses without the flag, printing the changelog's `## Breaking` section) → `preflight` → `backup` (the pre-upgrade set `pre-<tag>`) → `audit-intent` → `checkout` → `provision` → `preflight` → `apply` (the new tree's, rows streamed) → `verify` (the new `--version`, the applied record, every declared service healthy) → `engine-verify` (the new tree's `engine verify` as a passthrough child, the §6.7 gate; its rows above carry the check) → `audit-applied`. A failed row's fix is the standing next step by position: re-run before the checkout; correct and re-run at the new tree's provision or preflight; `upgrade --rollback` at or after its apply.
- **`upgrade --rollback [<tag>]`** (ADR-0005): `select` (the newest complete `pre-<tag>[-<ts>]` set, or the tag's) → `plan` (a restore is needed unless the rendered manifest still names the set's release; the verdict goes to `rollback.json`, which a re-run resumes from) → `safety` (a whole running stack gets a `pre-rollback-<ts>` set from the *current* tree) → `audit-intent` (deferred when Postgres is down) → `stop` → `identity` (the box identity removed when the set names one recipient, since that tree's snapshots would carry it; kept otherwise) → `checkout` → `restore` (the previous tree's `restore --from staging --set <label>`) → `apply` → `verify` → `engine-verify` (the previous engine now runs on host state the newer release converged, so the gate runs here too; its fix the engine's logs and `engine verify` by hand, never going live) → `audit-applied`, then the record removed. Host state converged for the newer release stays: ADR-0005's scope is the product.
